# 개인 진행률 — 무엇을 어떻게 재는가

알람 결정 화면의 진행 바가 "지금 어디쯤이고, 늦겠는가" 를 말한다. 그 판단의
기준과 계산을 여기에 적어 둔다. 색 하나가 사용자의 행동을 바꾸므로, 근거 없는
색을 칠하지 않는 것이 이 문서의 목적이다.

## 0. 고치는 계기

실기기에서 이렇게 나왔다.

```
약속          11:57
도착 예정      11:47   (= 약속 − 안전 버퍼 10분)
진행 바        11:51  ·  +4분  ·  노랑
```

11:51 에 도착하면 약속 11:57 보다 **6분 이르다.** 그런데 화면은 "+4분" 이라고
적고 노란색을 칠했다. 기준을 `도착 예정` 으로 잡았기 때문이다.

`도착 예정` 은 버퍼를 이미 뺀 값이다. 그것을 기준으로 지각을 재면 **버퍼를 두 번
쓰는 셈**이 된다. 버퍼는 "이만큼 일찍 도착하자" 는 목표이고, 지각은 "약속에
늦었는가" 다. 둘은 다른 질문이다.

## 1. 지각 기준

기준은 **약속 시각**(`Event.start_at`)이다.

```
늦는 분 = 예상 도착 − 약속 시각
```

| 늦는 분 | 색 | 표시 |
| --- | --- | --- |
| 0 이하 | 초록 | `정시` |
| 1 ~ 9 | 노랑 | `+5분` |
| 10 이상 | 빨강 | `+16분` |

예: 약속 11:30, 추적 결과 예상 도착 11:46 → **빨강 `+16분`**.

**10분은 고정값이다. 안전 버퍼를 쓰지 않는다.** 기준을 약속 시각으로 옮긴
순간 버퍼는 경계에서 할 일이 없어졌다. 버퍼를 경계로 쓰면 서버가 버퍼 정책을
바꿀 때 지각의 뜻이 함께 흔들린다.

일찍 도착하는 것은 `-6분` 이 아니라 `정시` 로 적는다. 음수 부호가 붙으면 읽는
사람이 지각으로 착각한다.

> 앱의 도착 판정 알림(`ArrivalVerdict`)은 처음부터 `startAtMillis`(약속) 기준
> 이었다. 진행 바만 다른 기준을 쓰고 있었다. 이제 둘이 같은 말을 한다.

## 2. 단계

| 단계 | 조건 |
| --- | --- |
| 알람 전 | 알람 시각 전 |
| 준비 중 | 알람이 울렸고 아직 움직임이 없음 |
| 이동 중 | 움직임이 감지됨 |
| 도착 | 목적지 반경 안에서 체류 확인 |
| 지난 일정 | 일정 시각이 지났고 이동 기록이 없음 |

### 움직임 감지

지금까지는 **집 반경 150m 를 벗어나야** 이동 중이 됐다(`TripGeofence`,
`DEPARTURE_RADIUS_M = 150.0`, 연속 2회). 아파트 단지나 캠퍼스는 그 자체가
150m 를 넘으므로, 집을 나서서 몇 분을 걸어도 화면은 "준비 중" 이었다.

반경 이탈 **또는** 지속적 이동 중 **먼저 오는 것**으로 전이한다.

지속적 이동의 조건은 둘을 함께 본다.

- 누적 이동 `MOVING_DISTANCE_M = 80` 이상
- 그 이동이 `MOVING_WINDOW_MILLIS = 60_000`(60초) 이상 이어짐

**단발 변위로 판정하지 않는다.** 정확도 게이트가 50m 이므로 두 좌표의 변위가
오차만으로 100m 까지 튈 수 있다. 집에 앉아 있는 사람이 "이동 중" 이 된다.
누적과 지속 시간을 함께 요구하면 그 산포가 걸러진다.

80m·60초의 근거: 출발 전 위치 주기가 30초(`IDLE_INTERVAL_MS`)라 60초는 좌표
2~3개다. 도보 속도 1.1m/s 로 60초면 66m 이므로 80m 는 "실제로 걷기 시작했다" 의
최소선이다.

### 준비 중이 없는 여정

준비 시간이 없는 일정(§4)은 **준비 중 단계를 건너뛴다.** 알람 전 다음이 바로
이동 중이다. 집에 있지도 않은 사람에게 "준비 중" 이라고 말할 근거가 없다.

## 3. 실시간 도착 예정

### 재료

| 값 | 출처 |
| --- | --- |
| 경로 좌표 | `AlarmPlan.route_path` (계산 시 카카오에서 받아 보관) |
| 경로 길이 | 보관한 좌표를 이은 길이 (`route_distance_m`) |
| 현재 위치 | `TripLiveState.Snapshot.point` (추적 서비스가 매 좌표마다 발행) |
| 계획 이동 시간 | `AlarmPlan.travel_minutes` |

진행률은 위치를 경로 선분에 투영한 **누적 이동 거리** 기준이다
(`RouteProgress`). 직선거리를 쓰면 경로가 돌아가는 구간에서 거꾸로 준다.

### 속도를 어떻게 쓰는가

```
관측 속도 = 경로를 따라 이동한 거리 ÷ 이동 시작 후 경과 시간
계획 속도 = 경로 전체 길이 ÷ 계획 이동 시간
```

둘을 **축소 추정**으로 섞는다. 표본이 쌓일수록 관측 쪽 가중을 올린다.

```
w = 경과 분 ÷ (경과 분 + PACE_SHRINKAGE_MINUTES)      # PACE_SHRINKAGE_MINUTES = 5
유효 속도 = (1 − w) × 계획 속도 + w × 관측 속도
예상 도착 = 지금 + 남은 거리 ÷ 유효 속도
```

**관측 속도만 쓰지 않는 이유.** 지하철을 기다리는 8분 동안 관측 속도는 0 에
가깝고, 그대로 나누면 도착 예정이 무한이 된다. 축소 추정은 이때 유효 속도를
`(1 − w)` 배로만 떨어뜨리므로 값이 유한하게 남는다 — 10분 정지면 `w ≈ 0.67`,
남은 시간이 약 3배가 되어 "많이 늦는다" 고 말하지만 발산하지 않는다.

**계획 속도만 쓰지 않는 이유.** 실제로 느리게 가고 있는데 남은 구간은 계획대로
간다고 보면, 늦는 원인이 "이미 흘려보낸 시간" 으로만 잡힌다. 사용자가 계획보다
느린 수단을 탔을 때 그 사실이 화면에 반영되지 않는다.

`PACE_SHRINKAGE_MINUTES = 5` 는 서버가 이동 시간 보정에 쓰는
`ROUTE_SHRINKAGE_K = 5` 와 같은 값으로 둔다. 같은 종류의 판단에 다른 숫자를
쓰면 둘 중 하나가 틀린 것이다.

### 아직 떠나지 않았을 때

진행률이 0 이고 관측 속도가 없다. 이때 예상 도착은 `지금 + 계획 이동 시간` 이다.
그러면 출발이 늦은 만큼 그대로 늦는다 — 사진5 의 `준비 중 · +26분` 이 이 경우다.

### 경로를 벗어났을 때

`RouteProgress.OFF_ROUTE_LIMIT_M = 300` 을 넘으면 **전망을 내지 않는다.** 다른
길을 가는 중이면 이 경로의 남은 거리에 계획 속도를 곱한 값이 아무 뜻이 없다.
색도 쓰지 않고 이탈 사실만 알린다.

### 어디서 계산하는가

**서비스가 내보내는 것은 `이동 시작 시각` 하나다.** 나머지는 화면이 계산한다.

처음에는 서비스가 ETA 까지 내야 한다고 봤다 — 화면에서 계산하면 화면이 열려
있는 동안만 표본이 쌓여 전망이 불안정할 것 같았다. 그런데 이 계산에 **이력이
필요하지 않다.** 진행 거리는 지금 위치를 경로에 투영해서 나오고, 경과 시간은
이동 시작 시각 하나로 나온다. 둘 다 과거 좌표를 쌓아 둘 필요가 없다.

그래서 `TripLiveState.Snapshot` 에 `movingSinceMillis` 를 더하는 것으로 끝난다.
경로 좌표를 `AlarmSchedule` 에 실어 서비스로 넘기지 않는다 — 600점이면 JSON 으로
약 25KB 이고, 디스크에 저장되는 값이라 이동 경로가 그대로 남는다.

## 4. 준비 시간은 집에서 출발할 때만

`준비 시간` 은 집에서 씻고 옷을 입고 나서는 시간이다. 이미 밖에 있는 사람에게는
해당되지 않는다. 그런데 서버는 출발지와 무관하게 늘 준비 시간을 넣었다.

**일정에 별도 출발지(`Event.origin_lat/origin_lng`)가 있으면 준비 시간을 뺀다.**
그 필드는 "이 일정만의 출발지" 라는 뜻이고, 없으면 프로필의 집을 쓴다
(`Event.resolve_origin`). 즉 값이 있다는 것 자체가 "집에서 출발하지 않는다" 다.

계산 방법 카드에는 이동과 버퍼만 남는다. 준비 항목을 0분으로 그리지 않는다 —
0분은 "준비를 순식간에 한다" 로 읽히고, 사실은 **해당되지 않는다**.

### prep 를 0 으로 넣으면 안 되는 이유

`estimate_prep` 가 돌려주는 `PrepEstimate` 를 `Normal(0, 0)` 으로 만들어
넘기면 세 가지가 조용히 깨진다.

1. `PrepEstimate.has_variance` 가 false 가 되어 `on_time_probability` 가 항상
   `None` 이 된다. 이동에 변동성이 있어도 확률을 못 낸다
2. `confidence_basis` 가 `prep_variance_unknown` 으로 바뀐다. "준비 변동성을
   모른다" 가 아니라 "준비 단계가 없다" 인데 화면은 전자로 설명한다
3. `prep_source`·`prep_breakdown` 이 그대로 남아, 화면이 "샤워 14분" 을 보여주면서
   준비 시간은 0분이 된다

그래서 `compute_alarm_math` 가 **prep 를 받지 않는 경로**를 갖는다. 총 소요는
이동뿐이고, 이동 변동성만으로 확률을 낸다. 이것은 오히려 개선이다 — 지금은
준비 분산이 없으면 확률을 못 냈다.

`prep_source` 에 값을 하나 둔다: `not_from_home`. 화면이 이유를 밝힐 수 있어야
사용자가 "준비 시간이 왜 없지" 를 묻지 않는다.

## 5. 임박한 일정의 경로 갱신

배차와 교통 상황이 바뀌면 가장 빠른 경로도 바뀐다. 알람 시각과 경로선이 그것을
따라가야 한다. 지금은 **재계산이 사용자가 버튼을 누를 때만** 일어난다
(`PlanSyncWorker` 는 6시간마다 돌지만 조회와 알람 등록만 한다).

### 먼저 할 일 — 재계산에 throttle 이 없다

`EventRecomputeView` 에는 `throttle_scope` 도 `throttle_classes` 도 없고,
`DEFAULT_THROTTLE_CLASSES` 도 설정에 없다. 즉 지금 이 엔드포인트는 **무제한**
이다. 사람이 누를 때만 불리던 동안에는 드러나지 않았지만, 자동 호출을 붙이는
순간 카카오 하루 한도를 태울 수 있는 구멍이 된다. `route` scope(120/hour)를
먼저 붙인다.

### 갱신 대상과 주기

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 대상 | 알람까지 `REFRESH_HORIZON_HOURS = 3` 이내 | 그 밖의 일정은 지금 갱신해도 출발 전에 또 바뀐다 |
| 한 번에 | 최대 `REFRESH_MAX_EVENTS = 2`건 | 임박 일정이 셋 이상인 아침은 드물고, 상한이 없으면 한 번에 쿼터를 태운다 |
| 주기 | 15분 (WorkManager 최소 주기) | 배차 간격보다 짧을 필요가 없다 |
| 건너뛰는 경우 | 임박 일정이 없음 · 이미 이동 중 | 아래 |

**이동 중이면 갱신하지 않는다.** 경로가 바뀌면 진행률의 분모가 바뀌어 바가
뒤로 물러난다. 이미 타고 있는 사람에게 다른 경로를 제안하는 것은 의미도 없다.

**임박 일정이 없으면 호출이 0 이다.** 15분 워커는 조회 한 번(로컬 캐시)으로
끝난다.

### 고른 경로를 바꾸지 않는다

갱신은 "가장 빠른 경로로 갈아 끼우는 것" 이 아니다.

| 일정 | 갱신이 하는 일 |
| --- | --- |
| 경로를 고른 일정 | `resolve_route` 로 **그 수단만** 다시 조회한다. 소요 시간만 새로 받는다 |
| 고르지 않은 일정 | `best_route` 로 가장 빠른 쪽을 고른다. 서버가 정하는 것이 원래 계약이다 |

사용자가 고른 값은 `Event.route_key` 에 있고 **재계산이 그것을 건드리지 않는다.**
`AlarmPlan.route_key` 만 실제로 쓴 경로를 기록한다. 그래서 첫 차가 아직 안 다니는
시간대에 대체가 일어나도, 노선이 다시 나타나면 다음 계산에서 원래 선택으로
돌아온다.

예외는 하나다. **고른 노선이 후보 목록에서 사라지면** 가장 빠른 대중교통으로
대체한다(`clients.resolve_route`). 대체하지 않고 계산을 포기하면 그 아침 알람이
아예 안 울리므로, 대체하고 **그 사실을 알린다.**

### 갱신을 화면이 말해야 한다

값은 여러 곳에 반영되는데(적용 알람 시각, 계산 방법의 이동 시간, 홈 목록의
경로 요약, 경로 지도 선) **그것이 갱신된 결과라는 표시가 없었다.** 두 가지를
더했다.

- `computed_at` 을 응답에 넣고 알람 카드에 "12분 전 계산" 을 적는다. 서버는 이
  값을 들고 있었지만 직렬화하지 않아 앱이 볼 수 없었다
- `route_choice_honored = false` 를 화면이 읽어 경고한다. 서버는 이 값을 처음부터
  내려주고 있었고 앱도 `routeFellBack` 으로 받아 뒀지만, **어느 화면도 읽지
  않았다** — 고른 경로가 대체돼도 사용자는 알 수 없었다

쿼터 계산: 일정 1건이 3시간 동안 15분마다 갱신되면 12회, `best_route` 가 최대
2회를 부르므로 24회다. 사용자 3명이 각자 하루 2건이면 144회 — 하루 1,000건
안에 넉넉히 들어온다.

## 6. 작업 순서

1. 지각 기준을 약속 시각으로 (§1) — 지금 화면이 틀린 값을 보여주고 있다
2. 준비 시간 조건부 (§4, 서버) — 단계와 계산 방법 카드가 이 값에 딸려 있다
3. 움직임 감지 (§2)
4. 실시간 도착 예정 (§3)
5. 경로 주기 갱신 (§5) — throttle 먼저
6. 피그마 반영, 전체 검증, 실기기 확인

## 7. 검증

숫자가 아니라 **말이 맞는지**를 본다.

- 약속보다 일찍 도착하는 예상은 초록 `정시` 다. 버퍼 때문에 노랑이 되지 않는다
- 집에 앉아 있는 동안 단계가 "이동 중" 으로 넘어가지 않는다
- 지하철을 기다리는 동안 도착 예정이 무한으로 가지 않는다
- 출발지를 따로 고른 일정의 계산 방법에 준비 항목이 없다
- 임박 일정이 없는 시간대에는 경로 API 호출이 0 이다
- 경로를 고른 일정은 갱신 뒤에도 같은 노선이다. 대체됐으면 화면이 그렇게 말한다
- 알람 카드가 언제 계산한 값인지 밝힌다

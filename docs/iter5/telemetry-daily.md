# S-4 텔레메트리 일별 집계

2026-11-28 · `front-iter5`

앱의 크래시·ANR은 Crashlytics에서 확인한다. 이 명령은 기존 서버 기록으로 사용량과 응답 시간을 집계한다. 앱에 새 이벤트 API를 추가하지 않는다.

## 실행과 보관

서버에서 아래 마이그레이션을 적용한 코드로 실행한다. 명령 자체는 DB를 읽기만 하고, 기록을 삭제하거나 외부 API를 호출하지 않는다.

```bash
cd backend
python manage.py migrate
python manage.py telemetry_daily --from 2026-12-07 --to 2026-12-11
python manage.py telemetry_daily --from 2026-12-07 --to 2026-12-11 --app-version 0.22.0 --users 12,15 --csv telemetry-beta.csv
```

`--users`의 숫자는 실제 베타 테스터 ID로 바꾼다. 출력에는 사용자 ID도 넣지 않는다. 버전 옵션을 생략하면 `all` 합계와 버전별 표를 함께 낸다. `--app-version unknown`은 버전 없는 기록만 선택한다. `--users`로 QA 계정 ID를 지정해도 제외 규칙을 우회하지 않는다.

날짜는 **KST 시작일 00:00 이상, 종료일 다음 날 00:00 미만**이다. 종료일도 포함한다. 기록이 없는 날도 0을 출력한다. 관측과 알람은 늦게 업로드되어도 실제 발생한 날에 센다. 따라서 늦은 업로드가 들어오면 과거 날짜의 집계가 달라질 수 있다.

표준 출력은 헤더가 있는 CSV이며 `--csv` 파일과 같은 행·열·정렬을 쓴다. 사람이 읽는 표와 별도 형식을 유지하지 않아 베타 원본을 그대로 비교할 수 있다. 파일 인코딩은 UTF-8이다.

`ApiRequestLog`는 기본 30일 뒤 삭제된다. **베타 직후인 2026-12-12~13에 12/7~11 전체 기간을 CSV로 남긴다.** 실행한 코드 커밋·필터·실행 시각도 팀의 테스트 문서에 기록한다. 이 명령은 이미 지워진 요청을 복구하지 않는다. 초기 실행은 진행 점검용, 베타 직후 실행은 늦은 업로드를 포함한 최종 보관용으로 구분한다. 운영 서버 실행이나 예약 작업 등록은 이번 코드 변경에 포함하지 않는다.

## 출력의 의미

모든 행은 `date`, `app_version`, `table`, `metric`으로 구분한다. 집계값은 `value`, 지연 시간 표본 수나 오류율의 분모는 `samples`다. 사용하지 않는 칸은 빈칸이다. 날짜·버전·고정된 지표명·HTTP 메서드·서버 URL 패턴 외에는 숫자만 출력한다.

| table | 행 | 의미 |
| --- | --- | --- |
| `daily` | `daily_active_users` | 해당 날짜·버전의 요청 로그에 있는 서로 다른 인증 사용자 수 |
| `daily` | `signups` | `User.date_joined` 기준 가입 수 |
| `daily` | `events_created` | `Event.created_at` 기준 일정 수. 요청 재시도 수가 아닌 실제 저장된 일정 수이며 반복·가져오기 일정도 포함 |
| `daily` | `alarm_fired`, `alarm_dismissed`, `alarm_snoozed`, `alarm_silenced` | `AlarmLog.kind`, `occurred_at` 기준. `scheduled`·스위치 켬/끔은 포함하지 않음 |
| `daily` | `trip_depart`, `trip_arrive` | `TripObservation.kind`, `observed_at` 기준. GPS 판정과 직접 입력 모두 포함 |
| `daily` | `alarm_time_updates` | 성공한 `PUT events/{id}/alarm/time` 요청 수 |
| `daily` | `alarm_proposal_accepts`, `alarm_proposal_rejects` | 각각 성공한 변경 제안 수락·거절 요청 수 |
| `daily` | `alarm_time_changes` | 직접 변경 요청 + 제안 수락 요청 수. 거절은 별도 지표로만 셈. 실제 이전 값과의 차이를 검사한 수치는 아님 |
| `daily` | `weekly_reports_opened` | 성공한 `GET reports/weekly` 요청 수. 재시도·새로고침 포함 |
| `daily` | `requests`, `server_errors` | 선택 범위의 저장된 전체 요청 수와 500~599 응답 수 |
| `daily` | `server_error_rate` | 5xx / 요청 수, 0~1 비율. 분모 0이면 빈칸, `samples=0` |
| `daily` | `anonymous_requests` | 사용자와 연결되지 않은 요청 수. `--users` 선택 시 0 |
| `usage` | `requests` | 날짜·버전별 route+method 사용량 상위 20개. 성공·실패·재시도 모두 포함. 동률은 메서드·경로순 |
| `latency` | `duration_ms` | route+method별 `samples`, `p50_ms`, `p95_ms`. 사용량 상위 20개 밖의 경로도 모두 포함 |

성공은 HTTP 200~299다. 알람·관측은 서버의 멱등 키로 중복 제거된 행을 세지만, 요청 기반 지표는 HTTP 요청 횟수다. 일정이나 사용자가 삭제되어 관련 행이 cascade로 삭제되면 그 기록은 셀 수 없다.

분위수는 정렬한 표본의 `(n−1)×q` 위치를 선형 보간하고 ms 소수 셋째 자리까지 표시한다. N8의 `POST events`·`POST events/{id}/recompute`는 p95 ≤ 300ms, N9의 `GET routes/candidates`는 p95 ≤ 2,000ms일 때 `p95_within_limit=1`, 초과하면 0이다. 세 경로는 요청이 없어도 표본 0으로 출력하고 분위수·통과 칸은 비운다. 경로 캐시 적중 여부는 로그에 없어 적중/미적중으로 나누거나 캐시 조건 충족을 주장하지 않는다.

요청 지연은 기존 미들웨어가 측정한 서버 처리 시간이다. 클라이언트 왕복 시간이나 순수 계산 시간과 같지 않다. 헬스·정적 지도·미등록 URL은 기존 로거가 제외하고, 익명 요청은 프로세스별 일일 상한이 있다. 따라서 오류율과 사용량은 **보관된 요청 로그의 선택 범위**를 설명하며 모든 서버 트래픽의 완전한 통계는 아니다. 정적 지도·카카오 실제 외부 호출 횟수도 이 자료만으로 입증할 수 없다.

## 앱 버전과 개인정보

요청 기반 지표는 `ApiRequestLog.app_version`을 사용한다. 모델 기록에는 버전이 없었으므로 다음 내부 메타데이터를 추가한다. 기존 요청의 `X-App-Version`을 `request_log.app_version()`으로 동일하게 정리해 **처음 생성할 때만** 저장한다. HTTP 응답 필드·요청 본문·엔드포인트는 바꾸지 않는다.

| 모델 | 내부 필드 | 적용 경로 |
| --- | --- | --- |
| User | `registration_app_version` | 일반 가입·소셜 신규 가입 |
| Event | `creation_app_version` | 직접 생성·캘린더 가져오기 |
| AlarmLog | `app_version` | 기존 알람 일괄 업로드 |
| TripObservation | `app_version` | 기존 관측 일괄 업로드 |

마이그레이션 전 데이터와 헤더 없는 내부 생성 기록, 서버의 반복 일정 확장은 `unknown`이다. 사용자 최신 버전으로 과거 기록을 추정하지 않는다. 오프라인 기록의 버전은 발생 당시 설치 버전이 아니라 **처음 성공적으로 업로드한 요청의 버전**이다. 현재 업로드 본문에 발생 당시 앱 버전이 없기 때문이다. 같은 멱등 키의 재전송은 최초 버전을 유지한다.

`0.22.0 (22)`는 `0.22.0`으로 묶는다. 숫자 버전과 `alpha/beta/rc/dev`의 숫자 접미사 외의 임의 헤더 문자열은 `unknown`으로 묶어 헤더에 들어온 이름이 출력되지 않게 한다. 여러 버전을 같은 날 사용한 사람은 버전별 DAU에 각각 잡힐 수 있지만 `all` DAU에서는 한 번만 센다. 나머지 기록은 하나의 버전에만 귀속된다. `all` 행을 버전별 행에 다시 더하면 안 된다.

이메일·닉네임·좌표·장소 이름·요청/응답 본문·실제 URL 인수는 집계 출력에 넣지 않는다. 경로는 현재 서버 URL resolver에 등록된 패턴만 사용한다. 과거 실제 URL은 등록 패턴으로 정리하고, 알 수 없는 경로는 `other`, 알 수 없는 메서드는 `OTHER`로 묶는다. CSV 셀에도 원문을 넣지 않는다.

## N26 테스트 계정 제외와 학습

`apps/common/cohort.py`의 공통 이메일 접두 규칙을 집계·학습·정리 스크립트가 공유한다. `qa-ui-…`, `qa_…`, `qa-…`, `e2e_…`, `depcheck_…`와 기존 API 검증 스크립트 접두는 대소문자와 관계없이 제외한다. 실제 사용자를 닉네임·이메일 도메인·스태프 여부로 제외하지 않는다. 새 QA 계정 생성 스크립트는 이 공통 목록에도 접두를 추가해야 한다.

성공한 가입·로그인·소셜 인증은 서버 내부의 사용자 ID로 요청 로그를 연결해 QA 여부를 판별한다. 인증 본문이나 자격 증명을 추가 저장하지 않는다. **과거 익명 요청이나 실패한 비로그인 요청은 계정을 식별할 수 없다.** 토큰 갱신·로그아웃·계정 없는 비밀번호 검사 등 사용자 연결을 하지 않는 요청도 익명으로 남는다. 기본 서버 요청 통계에는 이 트래픽이 포함되고 `anonymous_requests`로 크기를 확인할 수 있다. QA 실패 요청까지 섞이지 않는 베타 테스터 집계는 반드시 `--users`를 지정한다. 잘못된 ID를 넣었다고 다른 사용자를 대신 포함하지 않는다.

학습 관측 수집·개인 학습·준비 시간 관측·버퍼 보정도 동일한 제외 규칙을 사용한다. 기존 QA 개인 이동·버퍼 보정도 실행 중에 무시한다. 이미 배포된 전역 모델은 코드를 바꾸는 것만으로 과거 QA 영향이 지워지지 않으므로, 운영 담당자가 마이그레이션 후 `python manage.py train_models --users --verbosity 0`으로 전체 재학습해야 한다. 이때 기존 QA 개인 아티팩트를 비활성화하고, 유효한 관측이 없으면 과거 전역 아티팩트도 비활성화한다. 원본 관측은 보존한다. `--dry-run`은 저장하지 않으므로 정리 완료를 대신하지 않는다. 실제 서버에서의 마이그레이션·재학습은 팀 배포 절차에 따라 수행한다.

## 검증과 다음 작업

```bash
cd backend
python -m pytest apps/common/tests/test_telemetry_daily.py apps/common/tests/test_telemetry_version.py apps/prediction/tests/test_test_account_exclusion.py
```

pytest는 저장소의 `config.settings.test`에 의해 외부 키 없는 메모리 SQLite를 사용한다. KST 경계, 발생일과 업로드일 차이, 버전 필터·미상 버전·재시도, QA 제외, 베타 사용자 선택, 백분위수와 예산, 상위 20개, 표준 출력과 CSV 일치, 개인정보 누출을 확인한다. 2026-11-28 검증에서 백엔드 전체 **2,500개 통과, 실패·오류·건너뜀 0개**였다. 이 중 새 회귀 검증은 집계 31개·버전 기록 10개·N26 34개로 총 75개다. 마이그레이션 누락 검사도 통과했다. [검증 요약](evidence/telemetry-tests.json)에 결과를 남겼다. 운영 DB·PostgreSQL에서 실행한 결과는 아니며, 실제 베타 수치를 측정한 것도 아니다.

S-6 베타 종합 명령은 별도 작업으로 남긴다. 베타 시작 전까지 사용자·주별 정시율, 미룸 수, 준비·이동 MAE의 분모·표본 제외·예측 시점 고정 기준을 정하고 구현해야 한다. 수면 변화는 현재 기록으로 실제 수면 시간을 측정했다고 주장할 수 없다. S-4 CSV는 이 지표에 필요한 개인별 원자료를 대체하지 않으며 기존 계획 이력·관측·알람 원자료의 보존도 함께 확인해야 한다.

도움말 › **[문의하기]**. 앱 쪽 제안 계약(`front-iter4` 의 `docs/iter4/inquiry-api.md`)을 그대로 받는다. 경로 · 본문 · 상태 코드가 같아서 앱은 바꿀 것이 없다.
구현: `backend/apps/support/`(새 앱: 모델 `Inquiry`, 검사 `serializers.py`, 팀 알림 `notify.py`, 관리 화면 `admin.py`) · 테스트: `backend/apps/support/tests/test_inquiries.py` · 마이그레이션 `support 0001_initial`(새 표 `support_inquiry`)

## 1. 요청 · 응답

```
POST /api/support/inquiries          (끝의 / 는 있어도 된다)
Authorization: Bearer <access>

{
  "message": "알람이 예상보다 30분 일찍 울렸어요",
  "reply_email": "me@snu.ac.kr",
  "app_version": "0.21.0",
  "device": "samsung SM-S911N · Android 14"
}
```

```json
201 Created
{"id": 123}
```

| 필드 | 규칙 | 400 문구(`details.<필드>`) |
| --- | --- | --- |
| `message` | 필수. 앞뒤 공백을 뺀 **10~1000자**(코드 포인트로 센다 — 앱 `Inquiry.length` 와 같다). 저장도 공백을 뺀 값 | "문의 내용을 적어 주세요" · "10자 이상 적어 주세요" · "1000자까지 쓸 수 있어요" |
| `reply_email` | 필수. 이메일 형식, 254자까지. 로그인 이메일과 달라도 된다 | "답 받을 이메일을 적어 주세요" · "이메일 형식을 확인해 주세요" |
| `app_version` | 선택(빠지거나 null 이면 빈 값). 32자까지 | "앱 버전은 32자까지예요" |
| `device` | 선택. 120자까지 | "기기 정보는 120자까지예요" |

본문의 다른 필드(`user` 등)는 무시한다. 문의는 늘 로그인한 사용자 것으로 저장한다.

| 상태 | 언제 | 앱의 안내(`Inquiry.outcome`) |
| --- | --- | --- |
| 201 `{id}` | 저장했다. **팀 메일이 실패해도 201**(3절) | DONE |
| 400 `invalid` | 위 규칙 위반. `error.message` 는 첫 문구, `error.details` 에 칸별 문구 목록 | FAILED(앱이 같은 규칙을 먼저 검사하므로 거의 오지 않는다) |
| 401 | 토큰 없음 · 만료 | FAILED(앱의 토큰 갱신 경로를 먼저 탄다) |
| 429 `throttled` | 사용자당 **시간당 5건** 초과(`support_inquiry`). 검사에서 떨어진 요청도 센다 | LIMITED |

400 예:

```json
{"error": {"code": "invalid", "message": "10자 이상 적어 주세요",
  "details": {"message": ["10자 이상 적어 주세요"], "reply_email": ["이메일 형식을 확인해 주세요"]}}}
```

## 2. 저장 · 관리 화면

- `support_inquiry` 한 행: 사용자, 글, 답 받을 이메일, 앱 버전, 기기, 상태(`open` 접수 · `answered` 답함 · `closed` 닫음), 팀 메모, 받은 시각, 처리 시각.
- Django admin **9. 문의 › 문의**: 상태 · 받은 시각 · 앱 버전으로 거르고 글 · 이메일 · 사용자 이메일로 찾는다. 목록에서 여러 건을 골라 "답함 / 닫음 / 접수로 되돌리기". 수정 화면에서는 상태와 메모만 바꾼다(사용자가 보낸 값은 읽기 전용). 처음 접수 밖으로 바꾼 시각이 처리 시각으로 남는다. 손으로 추가할 수는 없다.
- 계정을 지우면 그 사용자의 문의도 지워진다(글과 이메일은 그 사람의 개인 정보다).

## 3. 팀 알림 메일

- 저장한 **뒤** 환경 변수 `SUPPORT_INBOX_EMAILS`(쉼표로 여러 주소)로 보낸다. 메일 설정은 비밀번호 재설정 코드와 같다(`EMAIL_BACKEND` · `EMAIL_HOST` · `DEFAULT_FROM_EMAIL`).
- 제목 `[JustInTime 문의 #123] <글 앞부분 40자>`, 본문에 사용자 번호 · 닉네임 · 로그인 이메일, 답 받을 이메일, 앱 버전, 기기, 글 전체, 관리 화면 경로. **`Reply-To` 가 답 받을 이메일**이라 팀은 메일에서 [답장] 만 누르면 된다.
- `SUPPORT_INBOX_EMAILS` 가 비어 있으면 보내지 않고 로그에 "메일은 보내지 않는다" 만 남긴다. 문의는 저장되고 admin 에서 볼 수 있다.
- 보내다 실패해도(SMTP 막힘 등) 201 이다. 로그에는 문의 번호와 오류 종류만 남긴다(글 · 주소는 남기지 않는다). 같은 글을 여러 번 보내게 만들지 않으려는 것이다.

## 4. 앱 문서 4절 질문에 대한 결정

| 질문 | 결정 |
| --- | --- |
| 문의를 받을 주소 | 코드에 적지 않는다. 팀이 정한 주소를 Render 대시보드의 `SUPPORT_INBOX_EMAILS` 에 넣는다(`render.yaml` 에 `sync: false` 로 자리만 있다). **넣기 전까지는 admin 에서만 보인다** |
| 로그인하지 않은 사용자의 문의 | 받지 않는다(401). 도움말은 로그인 뒤에만 열리고, 공개로 열면 사용자 단위 빈도 제한이 듣지 않아 팀 메일함이 스팸 통로가 된다 |
| 최근 알람 계획 · 로그 첨부 | 붙이지 않는다. 동의 문구가 없고, 팀은 메일의 사용자 번호로 admin 에서 그 사용자의 계획 · 기록을 볼 수 있다 |
| 사용자에게 접수 확인 메일 | 보내지 않는다. `reply_email` 은 확인하지 않은 임의 주소라, 보내면 남의 주소로 메일을 보내게 하는 통로가 된다. 앱의 "문의를 보냈어요" 안내로 충분하다 |

## 5. 앱 할 일

없음. 경로 · 본문(`SupportApi.InquiryRequest`) · 201 `{id}` · 404/405/429 해석이 제안 계약과 같다. 서버 배포 전에는 지금처럼 404 → "아직 앱에서 문의를 받을 수 없어요". 400 의 `details.message` · `details.reply_email` 문구는 `Inquiry.kt` 의 문구와 같아서, 나중에 칸 아래에 붙이려면 그대로 쓰면 된다.

## 6. 배포

- `support 0001_initial` 마이그레이션(새 표). 기존 표는 바뀌지 않는다. 배포 컨테이너가 시작할 때 `migrate` 가 돈다.
- Render 환경 변수 `SUPPORT_INBOX_EMAILS` 를 대시보드에서 채운다. 메일이 실제로 나가려면 비밀번호 재설정 메일과 같은 발송 설정이 살아 있어야 한다.

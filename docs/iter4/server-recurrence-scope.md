# 반복 일정 범위 수정·삭제 서버 계약 (iter4 A2, BE-A2)

반복 일정의 한 회차를 고치거나 지울 때 "이 일정만 / 이후 일정 모두" 를 고른다. 앱 쪽 제안
계약([recurrence-scope-api.md](recurrence-scope-api.md), front-iter4)과 요청 모양이 같다. 이 문서는
서버가 실제로 하는 일과, 제안 문서가 열어 둔 질문에 서버가 정한 답을 적는다.

구현: `backend/apps/events/recurrence.py`(`split_following`·`delete_following`·`lock_occurrence`),
`EventDetailView.update/destroy`, `EventWriteSerializer.validate`, `EventRecurrence.until`
(`events.0015_recurrence_until`) · 테스트: `backend/apps/events/tests/test_recurrence_scope.py`

**버전.** 이 기능은 `APP_VERSION` 0.21.0 배포에 들어간다. 앱은 `/api/health` 의 `version` 이
0.21.0 이상일 때만 범위 시트를 켠다(`RecurrenceScope.SINCE_SERVER`). 구버전 서버는 `scope` 를
모르는 필드로 무시한다.

## 1. 수정: `PATCH /api/events/{id}`

본문에 `scope` 를 더한다. 나머지 필드는 [event-edit-api.md](../iter3/event-edit-api.md) 와 같다(바뀐 필드만).

| `scope` | 반복 회차 | 반복이 아닌 일정 |
| --- | --- | --- |
| 없음 · `null` · `""` · `"this"` | 그 회차만 바꾼다(지금과 같다) | 그 일정을 바꾼다 |
| `"following"` | 이 회차부터 앞으로의 회차를 모두 바꾼다 | `"this"` 와 같다(오류 아님) |
| 그 밖의 값(`"all"`, 대문자, 숫자, 배열) | 400 | 400 |

`repeat_weekdays`(0 = 월 … 6 = 일)는 **반복 회차 + `"following"`** 일 때만 받는다. 서버가 중복을
없애고 오름차순으로 정리한다. 다른 경우에 실으면 지금처럼 400 이다. 반복이 아닌 일정을 반복으로
바꾸는 길은 없다(새로 만들어야 한다).

```json
{"title": "알고리즘 수업", "start_at": "2026-11-18T10:30:00+09:00", "scope": "following", "repeat_weekdays": [1, 3]}
```

응답은 지금처럼 **이 회차의** 일정 객체다(200). `recurrence_id` 가 새 규칙 id 로 바뀔 수 있고,
요일을 바꿨으면 `start_at`·`recurrence_date` 가 새 첫 날로 옮겨 간다. 다른 회차는 응답에 없으니
앱은 성공하면 목록을 다시 받아 기기 알람을 맞춘다(앱은 이미 그렇게 한다).

### 1.1 `"following"` 일 때 서버가 하는 일

이 회차의 원래 날짜(`recurrence_date`)를 **나누는 날** 이라 부른다. 모두 한 트랜잭션이다.

1. 규칙 행과 이 회차 행을 잠근다(`select_for_update`, 회차 펼치기·한 회차 삭제와 같은 순서).
2. 새 값 = **원래 규칙 값 + 이번 PATCH 의 바뀐 필드.** 보내지 않은 필드는 이 회차가 아니라
   규칙의 값을 쓴다. 검증(출발·도착 50m, 국내 좌표, 집 주소 등)은 지금 PATCH 와 같다.
3. 새 규칙의 첫 날 = 고친 시작 날짜부터 처음 맞는 요일(생성의 첫 날 규칙과 같다). 지운 날짜와
   반복 끝 날짜는 건너뛴다. 시각은 고친 시각(안 보냈으면 규칙 시각)이고 **규칙 시간대의 벽시계
   시각** 이다(프로필 시간대가 바뀌었어도 규칙을 만든 시간대를 쓴다. 서머타임을 지나도 9시는 9시다).
4. 이 회차가 규칙의 첫 회차면 규칙을 그 자리에서 고친다(규칙 id 그대로). 아니면 원래 규칙을
   **나누는 날 전날로 끝내고**(`until`) 새 규칙을 만든다. 끝난 규칙은 더 펼치지 않는다.
5. 이미 만들어진 이후 회차(나누는 날 이후)는 새 규칙에 다시 이어 붙이고 새 값으로 덮어쓴다.
   **id 는 그대로다.** 새 규칙에 없는 날(요일을 뺐거나 첫 날 전)의 회차는 지운다.
6. 7일 창(오늘 00:00 ~ 7일 뒤 00:00)을 새 규칙으로 다시 펼치고, 바뀐 회차마다 알람 계획을 지금
   수정과 같은 규칙으로 다시 만든다(event-edit-api 3절: 경로 · 다시 섞기 · 그대로). 새로 생긴 회차는
   계산하고, 그날 다른 일정의 수동 켬/끔을 돌린다(새 일정이 들어온 날, BE-25).

| 지운 날짜(`excluded_dates`) | 나누는 날 이후 것은 새 규칙으로 옮긴다. 지운 회차가 되살아나지 않는다 | |

| 날짜를 앞으로 옮기면(수 → 화) | **400** `start_at` | 나누는 날 전의 지난 회차를 바꾸게 된다 |

| 반복이 아닌 일정 + `"following"` | 보통 수정(`"this"`). `repeat_weekdays` 는 400 | 앱은 반복 회차에만 시트를 띄운다 |

### 1.3 오류

공통 형식 `{"error": {"code", "message", "details"}}` 이다. `details` 의 키가 필드다.

| 상황 | 상태 | `details` 키 | 메시지 |
| --- | --- | --- | --- |
| 모르는 `scope` | 400 | `scope` | scope 는 this 또는 following 이어야 해요. |
| `"this"`(또는 없음)·반복 아닌 일정에 `repeat_weekdays` | 400 | `repeat_weekdays` | 반복 요일은 반복 일정을 '이후 일정 모두'로 고칠 때만 바꿀 수 있어요. |
| `"following"` 에 빈 `repeat_weekdays` | 400 | `repeat_weekdays` | 요일을 하나 이상 골라 주세요. 반복을 끝내려면 '이후 일정 모두 삭제'를 쓰면 돼요. |
| 범위 밖 요일(`7`, `-1`, 문자) | 400 | `repeat_weekdays` | (기존 생성 검증과 같다) |
| `"following"` 에서 이 회차보다 앞 날짜로 | 400 | `start_at` | 이후 일정 모두를 고칠 때는 이 회차보다 앞 날짜로 옮길 수 없어요. |
| 반복 끝 날 뒤로 옮김(끝난 규칙의 회차) | 400 | `start_at` | 반복이 끝나는 날 뒤로는 옮길 수 없어요. |
| 남의 일정 · 없는 id | 404 | | |

400 이면 아무것도 바뀌지 않는다(규칙·회차·계획 모두).

## 2. 삭제: `DELETE /api/events/{id}?scope=following`

| `scope` | 반복 회차 | 반복이 아닌 일정 |
| --- | --- | --- |
| 없음 · `this` | 그 날짜만 뺀다(지금과 같다, `excluded_dates`) | 지운다 |
| `following` | 이 회차와 이후 회차를 지우고 규칙을 전날로 끝낸다(`until`) | 지운다(오류 아님) |
| 그 밖의 값 | 400 `scope` | 400 `scope` |

성공은 204. 첫 회차에서 `following` 이면 남는 회차가 없으므로 규칙도 지운다. 지난 회차는 남는다.
나누는 날 이후의 지운 날짜 표시는 정리한다. 다시 보내면 회차가 이미 없어서 404 다.

## 3. 데이터

- `EventRecurrence.until`(date, null 허용, DB 기본값 null): 반복이 끝나는 날(규칙 시간대, 그날 포함).
  null 이면 끝이 없다. 펼치기(`expand`)가 그날 뒤로는 회차를 만들지 않는다.
- 마이그레이션 `events.0015_recurrence_until` 하나. 구버전 코드가 INSERT 해도 DB 기본값이 채운다.
  **구버전 서버는 `until` 을 모른다** — 마이그레이션 뒤 구버전 컨테이너가 잠깐 돌면 끝난 규칙을 계속
  펼칠 수 있다. 0.21.0 컨테이너로 바뀐 뒤 목록 조회는 끝난 규칙의 날짜 뒤 회차를 새로 만들지 않는다
  (이미 만들어진 것은 남는다). 배포 사이 몇 분 동안 사용자가 "이후 모두" 를 누를 일은 드물다.
- 응답 형식은 바뀌지 않는다(`until` 을 내보내지 않는다). 앱은 회차 목록만 본다.

## 4. 앱이 할 일

- 없음. front-iter4 의 `RecurrenceScope.withScope`(PATCH 본문 `scope` + 바꾼 요일), `deleteScoped`
  (`?scope=following`), 성공 뒤 목록·기기 알람 다시 맞추기가 이 계약 그대로다.
- 참고: 앱은 요일을 바꿨을 때만 `repeat_weekdays` 를 싣는다. 서버는 안 실려도 원래 요일을 쓴다.
- 400 의 `details.start_at` 은 수정 화면의 시각 칸 아래, `details.repeat_weekdays` 는 요일 칸 아래에
  보이면 된다(기존 필드 오류 처리).

# 반복 일정 범위 수정·삭제 서버 계약 (iter4 A2, BE-A2)

반복 일정의 한 회차를 고치거나 지울 때 "이 일정만 / 이후 일정 모두" 를 고른다. 앱 쪽 제안
계약([recurrence-scope-api.md](recurrence-scope-api.md), front-iter4)과 요청 모양이 같다. 이 문서는
서버가 실제로 하는 일과, 제안 문서가 열어 둔 질문에 서버가 정한 답을 적는다.

구현: `backend/apps/events/recurrence.py`(`split_following`·`delete_following`·`lock_occurrence`·
`lock_series`), `EventDetailView.update/destroy`, `EventWriteSerializer.validate/update`,
`EventRecurrence.until`(`events.0015_recurrence_until`)·`EventRecurrence.split_from`
(`events.0016_recurrence_split_from`) · 테스트: `backend/apps/events/tests/test_recurrence_scope.py`,
`test_recurrence_scope_review.py`(리뷰 수정 A2-1 ~ A2-9)

**버전.** 이 기능은 `APP_VERSION` 0.21.0 배포에 들어간다. 앱은 `/api/health` 의 `version` 이
0.21.0 이상일 때만 범위 시트를 켠다(`RecurrenceScope.SINCE_SERVER`). 구버전 서버는 `scope` 를
모르는 필드로 무시한다.

## 0. 용어

- **반복(묶음).** 앱이 하나로 보는 반복 일정. 서버에서는 규칙(`EventRecurrence`) 하나 이상이다.
  "이후 일정 모두" 수정이 규칙을 나누면 새 규칙의 `split_from` 이 원래 규칙을 가리킨다. 이렇게 이어진
  규칙 전부가 한 묶음이다.
- **자리**(`recurrence_date`). 규칙이 그 회차를 만든 날. "이 일정만" 으로 날짜를 옮겨도 그대로다.
- **보이는 날.** 회차의 실제 시작(`start_at`)의 규칙 시간대 현지 날짜. 앱 목록이 보여 주는 날이다.
- **나누는 날.** 고치거나 지우는 회차가 **보이던 날**(수정 전 시작). 자리가 아니다(리뷰 A2-6).
- **회차별 표시.** "안 감"(`skipped_at`), 알람 켬/끔(`alarm_enabled`), 준비 학습 제외
  (`prep_learning_excluded_at`). 일정 값이 아니라 그날의 선택이다.

## 1. 수정: `PATCH /api/events/{id}`

본문에 `scope` 를 더한다. 나머지 필드는 [event-edit-api.md](../iter3/event-edit-api.md) 와 같다(바뀐 필드만).

| `scope` | 반복 회차 | 반복이 아닌 일정 |
| --- | --- | --- |
| 없음 · `null` · `""` · `"this"` | 그 회차만 바꾼다(지금과 같다) | 그 일정을 바꾼다 |
| `"following"` | 이 회차부터 앞으로의 회차를 모두 바꾼다 | `"this"` 와 같다(오류 아님) |
| 그 밖의 값(`"all"`, 대문자, 숫자, 배열) | 400 | 400 |

`repeat_weekdays`(0 = 월 … 6 = 일)는 **반복 회차 + `"following"`** 일 때만 받는다. 서버가 중복을
없애고 오름차순으로 정리한다. 다른 경우에 실으면 지금처럼 400 이다. 반복이 아닌 일정을 반복으로
바꾸는 길은 없다(새로 만들어야 한다).

```json
{"title": "알고리즘 수업", "start_at": "2026-11-18T10:30:00+09:00", "scope": "following", "repeat_weekdays": [1, 3]}
```

응답은 지금처럼 **이 회차의** 일정 객체다(200, id 그대로). `recurrence_id` 가 새 규칙 id 로 바뀔 수
있고, 요일을 바꿨으면 `start_at`·`recurrence_date` 가 새 첫 날로 옮겨 간다. 다른 회차는 응답에 없으니
앱은 성공하면 목록을 다시 받아 기기 알람을 맞춘다(앱은 이미 그렇게 한다).

### 1.0 `"this"` (한 회차)

반복 회차면 규칙과 회차를 잠근 한 트랜잭션에서 고친다(`lock_occurrence`). 저장은 **바뀐 필드만**
쓴다(`EventWriteSerializer.update` 의 `update_fields`). 그래서 동시에 온 "이후 일정 모두" 가 이 회차를
새 규칙으로 옮겼으면, 이 요청은 옮겨 간 회차를 다시 읽어 그 위에 바뀐 필드만 얹는다. 예전처럼 예전
규칙으로 되돌려 저장해 같은 날 회차(알람)가 둘 생기지 않는다(리뷰 A2-2).

### 1.1 `"following"` 일 때 서버가 하는 일

모두 한 트랜잭션이다.

1. 묶음의 규칙 전부를 id 순으로 잠그고 이 회차를 잠근다(`lock_series`). 그사이 묶음이 바뀌었으면
   (동시에 온 다른 나누기) 다시 읽어 다시 잠근다.
2. 새 반복의 값 = **이 회차의 지금 값 + 이번 PATCH 의 바뀐 필드.** 이 회차를 전에 "이 일정만" 으로
   고쳤으면 그 값(제목·시각·장소·τ 등)도 새 반복의 값이 된다 — 사용자가 화면에서 본 값이다(아이폰과
   같다, 리뷰 A2-4). 검증(출발·도착 50m, 국내 좌표, 집 주소 등)은 지금 PATCH 와 같다.
3. 새 반복의 첫 날 = 고친 시작 날짜부터 처음 맞는 요일(생성의 첫 날 규칙과 같다). 지운 날짜와
   반복 끝 날짜는 건너뛴다. 시각은 이 회차의 (고친) 시각이고 **규칙 시간대의 벽시계 시각** 이다(프로필
   시간대가 바뀌었어도 규칙을 만든 시간대를 쓴다. 서머타임을 지나도 9시는 9시다).
4. 이 회차가 규칙의 첫 회차면(나누는 날이 규칙 시작 날 이하) 규칙을 그 자리에서 고친다(규칙 id
   그대로). 아니면 새 규칙을 만든다(`split_from` = 원래 규칙).
5. **묶음 전체에서** 나누는 날 이후에 보이는 회차를 새 반복이 가져간다(앞서 나눠 둔 뒤쪽 규칙 포함,
   리뷰 A2-5). 묶음의 다른 규칙은 나누는 날 전날로 끝내고(`until`), 회차가 남지 않은 규칙은 지운다.
   새 반복의 끝은 나누는 날 뒤를 맡던 규칙들의 끝이다(하나라도 끝이 없으면 끝없음). 앞서 "이후 일정
   모두 삭제" 로 끝낸 반복은 그 끝을 지킨다.
6. 가져간 회차는 새 반복에 다시 이어 붙이고 새 값으로 **덮어쓴다**(id 그대로). 놓는 날은 자리가
   나누는 날 이후면 그 자리, 나누는 날 전 자리에서 뒤로 옮겨 와 있던 회차면 보이던 날이다. 새 반복에
   없는 날(요일을 뺐거나 첫 날 전, 끝 뒤, 지운 날짜)의 회차는 지운다. 같은 날에 둘이 놓이면 그날이
   원래 자리인 회차를 남기고 다른 하나를 지운다.
7. 덮어쓴 회차의 **직접 정한 알람 시각·알람 확인·"바꿀까요" 제안·거절 기록을 지운다**(리뷰 A2-7).
   새로 만든 회차와 같은 상태다(확인 전). τ 를 바꾼 경우도 같다. 이 회차 자신은 지금 PATCH 와 같다:
   τ 를 바꿨으면 추천 시각을 확인한 것으로 두고(`alarm_control.preset_chosen`), 시작이 바뀌면 직접 정한
   시각이 저절로 풀린다.
8. 7일 창(오늘 00:00 ~ 7일 뒤 00:00)을 새 반복으로 다시 펼치고, 바뀐 회차마다 알람 계획을 지금
   수정과 같은 규칙으로 다시 만든다(event-edit-api 3절: 경로 · 다시 섞기 · 그대로). 새로 생긴 회차는
   계산하고, 그날 다른 일정의 수동 켬/끔을 돌린다(새 일정이 들어온 날, BE-25).

## 2. 삭제: `DELETE /api/events/{id}?scope=following`

| `scope` | 반복 회차 | 반복이 아닌 일정 |
| --- | --- | --- |
| 없음 · `this` | 그 자리만 뺀다(`excluded_dates`) | 지운다 |
| `following` | 묶음 전체에서 이 회차가 보이던 날 이후의 회차를 지우고 반복을 전날로 끝낸다(`until`) | 지운다(오류 아님) |
| 그 밖의 값 | 400 `scope` | 400 `scope` |

성공은 204. 다시 보내면 회차가 이미 없어서 404 다.

- **`this`.** 회차와 그 규칙을 잠그고 다시 읽은 뒤(`lock_occurrence`), 회차가 **지금** 속한 규칙에서
  그 자리를 뺀다. 동시에 온 "이후 일정 모두" 가 회차를 새 규칙으로 옮겼어도 새 규칙이 그 회차를 다시
  만들지 않는다(리뷰 A2-1).
- **`following`.** 묶음의 규칙 전부를 잠근다(`lock_series`). 앞서 나눈 뒤쪽 규칙의 회차도 지운다
  (리뷰 A2-5). 앞·뒤는 보이는 날로 가른다(리뷰 A2-6): 뒤 자리 회차를 앞으로 옮겨 뒀으면 남고, 앞 자리
  회차를 뒤로 옮겨 뒀으면 지우며 그 자리는 지운 날짜가 된다. 회차가 남지 않고 더 만들 자리도 없는
  규칙은 지운다(첫 회차에서 `following` 이면 규칙도 지운다). 지난 회차는 남는다. 나누는 날 이후의 지운
  날짜 표시는 정리한다.
- 다른 수정과 계속 겹치면 PATCH 와 같은 400 `scope` 다(리뷰 A2-9, 전에는 500).

## 3. 데이터

- `EventRecurrence.until`(date, null 허용, DB 기본값 null): 반복이 끝나는 날(규칙 시간대, 그날 포함).
  null 이면 끝이 없다. 펼치기(`expand`)가 그날 뒤로는 회차를 만들지 않는다.
- `EventRecurrence.split_from`(규칙 id, null 허용, DB 기본값 null, **DB FK 제약 없음**): 이 규칙을 떼어 낸
  원래 규칙. 묶음을 찾는 데만 쓴다(`recurrence._family_ids`). 제약을 걸지 않은 이유는 이 필드를 모르는
  구버전 코드가 원래 규칙을 지울 때 FK 위반으로 막히지 않게 하려는 것이다. 없는 id 를 가리키면 묶음의
  끝으로 본다. 서버가 규칙을 지울 때는 자식의 `split_from` 을 지운 규칙의 부모로 다시 잇는다.
  기존 규칙(0016 전에 나눈 것 포함)은 null 이라 묶음으로 이어지지 않는다 — 0.21.0 배포 전 나눈 규칙은
  없으니(기능이 0.21.0 에 들어간다) 실제로는 문제없다.
- 마이그레이션 `events.0015_recurrence_until`, `events.0016_recurrence_split_from`. 둘 다 컬럼 추가뿐이고
  DB 기본값이 있어 구버전 코드의 INSERT 를 막지 않는다.
- **끝난 규칙은 목록 조회에서 잠그지 않는다**(리뷰 A2-8). `until` 이 창 첫날(오늘) 전인 규칙은 새 회차가
  없으므로 `expand_for_user` 가 건너뛴다. 창 안에 계획이 없는 회차(예전에 창 밖으로 옮겨 둔 회차)나 끝
  뒤에 남은 행이 있을 때만 그 규칙을 펼친다(잠금 없는 조회 한 번).
- **끝 뒤에 남은 행 정리.** 펼치기가 끝난 규칙에서 자리와 보이는 날이 모두 `until` 뒤인 회차를 지운다
  (나누기와 경쟁한 옛 저장이 남겼을 행. 이제는 잠금으로 막지만 남은 행이 목록·알람에 보이지 않게 한다,
  리뷰 A2-2). "이 일정만" 으로 끝 뒤로 옮긴 회차(자리는 끝 전)는 사용자가 옮긴 것이라 남긴다.
- 응답 형식은 바뀌지 않는다(`until`·`split_from` 을 내보내지 않는다). 앱은 회차 목록만 본다.

### 3.1 되돌리기(롤백) 주의

**0.21.0 미만으로 되돌리면 회차가 겹친다.** 구버전 코드는 `until` 을 모른다. "이후 일정 모두" 로
나눈 반복은 원래 규칙(끝남)과 새 규칙이 둘 다 살아 있으므로, 구버전의 목록 조회가 원래 규칙을 끝 뒤로도
다시 펼쳐 같은 날 회차(알람)가 둘 생긴다. "이후 일정 모두 삭제" 로 끝낸 반복도 다시 이어진다.
되돌려야 하면:

1. 되돌리기 전에 `until` 이 있는 규칙을 확인한다(`EventRecurrence.objects.exclude(until=None)`).
2. 되돌린 뒤 겹친 회차를 정리하거나, 되돌리는 동안 앱의 범위 시트가 꺼지도록(`/api/health` 버전 <
   0.21.0) 둔다. 앱은 0.21.0 미만 서버에서는 범위 시트를 띄우지 않는다.
3. 다시 0.21.0 이상으로 올리면 펼치기가 끝 뒤 행을 지운다(위 "끝 뒤에 남은 행 정리", 창 안의 행만).

## 4. 앱이 할 일

- 없음. front-iter4 의 `RecurrenceScope.withScope`(PATCH 본문 `scope` + 바꾼 요일), `deleteScoped`
  (`?scope=following`), 성공 뒤 목록·기기 알람 다시 맞추기가 이 계약 그대로다.
- 참고: 앱은 요일을 바꿨을 때만 `repeat_weekdays` 를 싣는다. 서버는 안 실려도 원래 요일을 쓴다.
- 400 의 `details.start_at` 은 수정 화면의 시각 칸 아래, `details.repeat_weekdays` 는 요일 칸 아래에
  보이면 된다(기존 필드 오류 처리). `details.scope`(다른 수정과 겹침)는 일반 오류 문구로 보이면 된다.
- 동작 변화(앱 코드 변경 없음, 알아 둘 것):
  - "이후 일정 모두" 의 새 값은 수정 화면에 보이던 **이 회차의 값** 이다(규칙 값이 아니다). 앱 수정 화면이
    이미 이 회차 값을 채워 보여 주므로 화면과 결과가 같아진다.
  - "이후 일정 모두" 뒤 이후 회차는 직접 정한 알람 시각·확인이 풀린다(새 회차처럼 확인 전). 목록을 다시
    받으면 `alarm_plan` 의 확인 상태가 그렇게 온다.
  - 앞서 나눈 반복에서도 "이후 일정 모두 삭제/수정" 이 끝까지 닿는다.

# "안 감" 표시 API 계약과 기록 오염 방지

일정에 아예 안 가는 날이 있다. 그날은 도착 기록이 없어서 주간 리포트에 "측정 못 함" 으로
섞였고, 아침에 눌린 블록 기록이나 나갔다 돌아온 출발 관측이 준비·이동 학습에 들어갔다.
이제 사용자가 일정을 "안 감" 으로 표시하면 그 일정은 리포트·학습·버퍼 조정에서 빠지고 알람도
울리지 않는다.

같이 넣은 것: GPS 출발이 아예 잡히지 않은 아침에 "마침" 을 한참 뒤에 누른 블록 기록은 지금까지
거를 방법이 없었다. 블록 신고 범위에서 크게 벗어난 기록을 알람·학습에서 뺀다(5절).

구현: `Event.skipped_at`(마이그레이션 `events 0010`), `events/views.py` `EventSkipView`,
`planning/prep_observations.py` `usable_block_observations` · 테스트:
`backend/apps/events/tests/test_skip.py`, `backend/apps/planning/tests/test_block_range.py`,
`scripts/check_events_api.py` 19번

## 1. `POST /api/events/{id}/skip` ("안 감" 표시)

로그인 필요. 본문 없음. 응답은 일정 객체(`GET /api/events/{id}` 와 같은 모양)다.

| 상태 | 뜻 |
| --- | --- |
| 200 | 표시했다. 이미 표시돼 있으면 그대로(처음 표시한 시각 유지) |
| 401 | 로그인 안 됨 |
| 404 | 없는 일정이거나 남의 일정 |

- 지난 일정, 오늘 일정, 앞으로의 일정 모두 표시할 수 있다(내일 휴강이면 미리 표시).
- **계획과 관측은 지우지 않는다.** 되돌리면 같은 계획을 그대로 쓴다(다시 계산 없음, 카카오 0회).
- 표시한 뒤에 올라오는 출발·도착·블록 관측도 받는다(앱 큐가 막히지 않게). 읽을 때 뺀다.

## 2. `DELETE /api/events/{id}/skip` (되돌리기)

로그인 필요. 응답은 일정 객체. 표시돼 있지 않아도 200(두 번 눌러도 같다). 404 는 위와 같다.

## 3. 응답 필드

일정 객체(목록·상세·생성·수정·skip 응답)에 두 필드가 붙는다. 둘 다 읽기 전용이다. `PATCH`
로 보내도 무시한다.

| 필드 | 뜻 |
| --- | --- |
| `skipped` | "안 감" 으로 표시했는가 |
| `skipped_at` | 표시한 시각(ISO 8601), 아니면 `null` |

기존 앱은 모르는 필드를 무시하므로 영향이 없다.

## 4. 표시하면 달라지는 것

| 곳 | 달라지는 것 |
| --- | --- |
| 알람 | 울리지 않는다(`alarm_on: false`). 사용자가 켜 둔 알람(`alarm_enabled: true`)도. **같은 날 다음 일정이 첫 알람이 된다**(`is_first_alarm`) |
| 주간 리포트 `GET /api/reports/weekly` | `event_count`·`unobserved_count`·정시율·지각·원인·캘리브레이션·`outcomes` 에서 빠진다. 새 필드 `skipped_count`(그 주 지난 일정 중 표시한 수) |
| 캘리브레이션·지각 원인·지난주 비교 | 빠진다 |
| 버퍼 조정(밤 학습) | 그 아침을 지각 이력에 넣지 않는다 |
| 이동 시간 학습(밤 학습) | 그 일정의 출발·도착을 쓰지 않는다. 학습 로그의 버린 이유에 "안 감" 으로 센다 |
| 준비 시간(알람 계산·밤 학습) | 그 일정의 블록 기록과 GPS 준비 표본을 쓰지 않는다 |

- 일정을 다른 날로 옮겨도(PATCH `start_at`) 표시는 그대로다. 가기로 했으면 되돌린다.
- 반복 일정은 회차 하나만 표시한다. 반복 전체를 멈추는 기능은 아니다.
- 지난 일정을 표시하면 그 주 리포트와 다음 밤 학습부터 바뀐다. 이미 만든 버퍼 조정 기록은
  고치지 않는다.

## 5. 블록 기록 범위 기준

알람 계산과 밤 학습은 블록 기록 중 이 셋을 뺀다(`usable_block_observations`).

| 조건 | 이유 |
| --- | --- |
| 일정을 "안 감" 으로 표시했다 | 그날 아침은 등교 준비가 아니다 |
| 같은 일정의 GPS 출발보다 늦게 찍혔다 | 나간 뒤에 눌러 이동 시간이 섞였다(전부터 있던 기준) |
| 블록 신고 범위의 **최소 × 0.5 미만**이거나 **최대 × 1.5 초과** | 누르는 걸 잊었다가 한참 뒤에 눌렀거나, 안 한 블록을 바로 눌렀다 |

- 예: 샤워를 10~20분으로 정했으면 5~30분만 쓴다. 최소가 0분이면 하한이 없다. 최대가
  0분이어도 상한은 1.5분이다(1분 기준).
- 처음에는 0.25~4배로 넓게 잡았다. 10-29에 GPS 준비 시간 기준과 함께 0.5~1.5배로 좁혔다(사용자:
  "55분 세팅한 거에서 지나치게 벗어난 건 학습에서 제외"). 정한 값이 실제와 크게 다르면 학습으로
  고쳐지지 않으니 범위를 고쳐야 한다.
- 기준은 **지금** 신고 범위다. 블록 범위를 고치면 예전 기록도 새 범위로 다시 본다.
- 업로드 때는 거절하지 않는다. 리포트의 실제 준비 시간(`actual.prep_minutes`)도 누른 기록
  그대로 보여 준다. 알람과 학습만 거른다.

## 6. 앱이 할 일

1. **기록 끝내기 화면**(`MorningProgressScreen`)에 "오늘 안 가요" 버튼:
   `POST /api/events/{session.eventId}/skip` → 아침 기록 세션 닫기(`MorningSessionStore.clear()`)
   → 홈 다시 불러오기. 남은 블록은 기록하지 않는다.
2. **일정 상세·홈 카드**: 지난 일정이나 오늘 일정에 "안 감으로 표시" / 표시된 일정은 흐리게 +
   "되돌리기"(`DELETE`). 표시 뒤에는 목록을 다시 받고 알람을 다시 건다(`loadHomeOnline` →
   `AlarmScheduler.sync`). 같은 날 다음 일정의 알람이 새로 생길 수 있다.
3. **주간 리포트**: `skipped_count > 0` 이면 "안 간 일정 N건은 빼고 계산했어요" 한 줄(선택).
   `outcomes` 에 표시한 일정이 없으므로 요일 칸은 지금 코드 그대로 둔다.
4. `EventDto` 에 `skipped: Boolean = false`, `skippedAt: String? = null` 추가. 오프라인이면 큐에
   넣지 말고 실패 안내(표시는 되돌릴 수 있어 급하지 않다).

## 7. 직접 확인 (배포 뒤)

1. 내일 일정을 만들고 `POST /api/events/{id}/skip` → `skipped: true`, `alarm_on: false`.
   같은 날 두 번째 일정이 있으면 그 일정이 `is_first_alarm: true`.
2. `DELETE /api/events/{id}/skip` → `skipped: false`, 알람이 원래대로.
3. 지난주 일정 하나를 표시하고 `GET /api/reports/weekly?week=<지난주 월요일>` → 그 일정이
   `outcomes` 에 없고 `skipped_count` 가 1.

# 대중교통 후보 고르기 (0.14.0)

경로 선택 화면(`GET /api/routes/candidates`)의 대중교통 후보를 3개에서 5개로 늘리고, 고르는 기준을
늘렸다. 3개일 때는 시간·환승·요금 기준만 들어가서 같은 노선을 조금씩 바꾼 비슷한 경로만 나왔다
(사용자 요청 10-29 "최대한 다양한 옵션이 나오게"). 카카오 호출 수는 그대로다. 한 번 받은 응답
안에서 고른다.

구현: `backend/apps/routing/clients.py` `_transit_pool`·`_transit_candidates`·`resolve_route` ·
테스트: `backend/apps/routing/tests/test_transit_variety.py`, `test_transit_merge.py`(6절)

## 1. 고르는 순서

카카오 응답을 노선 조합(구간마다 첫 노선을 이은 것, 예: `2호선>5513`)으로 묶고, 조합이 같으면 가장
빠른 것 하나만 남긴다. 그다음 아래 순서로 하나씩 담는다. 이미 담긴 경로면 건너뛴다. 동률이면 빠른 쪽이다.

| 순서 | 기준 |
| --- | --- |
| 1 | 가장 빠른 것 |
| 2 | 환승이 가장 적은 것 |
| 3 | 걷는 시간이 가장 짧은 것(집→정류장, 환승, 정류장→목적지 도보의 합) |
| 4 | 지하철만 타는 것 중 가장 빠른 것 |
| 5 | 버스만 타는 것 중 가장 빠른 것 |
| 6 | 지하철과 버스를 섞는 것 중 가장 빠른 것 |
| 7 | 요금이 가장 싼 것(요금을 모르는 경로는 뺀다) |
| 남는 칸 | 이미 담긴 경로에 없는 노선이 많은 것부터 |

- 5개가 차면 멈춘다. 그래서 1~6이 모두 다르면 요금 기준은 들어가지 못한다.
- 남는 칸에는 **너무 느린 경로를 넣지 않는다.** 가장 빠른 것의 1.5배 이상이거나 20분 이상 더
  걸리면 뺀다(`TRANSIT_FILL_MAX_RATIO`, `TRANSIT_FILL_MAX_EXTRA_SECONDS`). 1~7 기준 대표에는 이
  조건을 걸지 않는다. 30분 걸려도 환승 없는 버스를 고르는 사람이 있다.
- 남는 칸을 빠른 순으로 채우면 가장 빠른 경로의 뒤 버스만 바꾼 것들이 칸을 다 차지한다. 그래서 새
  노선 수를 먼저 본다.
- 응답의 대중교통 후보 순서는 전과 같이 전체 목록과 함께 빠른 순이다.

## 2. 배지

`badges` 에 `"최소 도보"` 가 새로 생겼다. 기준은 대중교통 후보 전체(추리기 전)에서 걷는 시간이 가장
짧은 것이고, 동률이면 모두 받는다. **배지는 최대 3개다**(순서: 최단 시간, 최소 비용, 최소 환승, 최소
도보). 경로 카드 한 줄에 들어가야 한다. `reason` 은 전처럼 첫 배지다.

## 3. 고른 경로로 알람 계산하기

`resolve_route` 는 이제 **추린 5개가 아니라 카카오 응답 전부에서** 고른 노선 조합을 찾는다. 그날
순위가 밀려 화면 목록에서 빠져도 카카오가 그 조합을 아직 주면 그 경로로 계산한다. 전에는 3개 안에
없으면 대중교통 최단으로 바꿨는데, 일부러 고른 느린 직행 버스 대신 빠른 경로로 계산하면 알람이 늦게
울린다. 카카오가 그 조합을 아예 주지 않을 때만 최단으로 바꾼다(`route_choice_honored: false`).

경로를 고르지 않은 일정(`best_route`)은 전과 같다. 도보와 대중교통 최단 중 빠른 쪽이다.

## 4. 앱

- `RouteMode.TRANSIT` 상한 3 → 5(`domain/model/RouteOption.kt`). **이 앱이 아니면 5개 중 빠른 3개만
  보인다.** 빠른 순으로 자르므로 환승 최소·도보 최소 경로가 빠질 수 있다. 서버와 앱을 같이 올린다.
- 대중교통 탭에 카드가 최대 5개다. 목록은 이미 세로 스크롤이다.
- 배지 문구 `"최소 도보"` 는 서버 문구 그대로 그린다(앱 변경 없음).

## 5. 늘어나는 것

- 응답 크기: 후보마다 미리보기 경로 좌표가 붙어서 대중교통 2개분이 늘어난다.
- 실시간 도착 정보(버스·지하철 API)는 최종 후보에만 붙이므로 조회가 최대 3개분 → 5개분으로 는다.
  캐시(버스 15초, 지하철 20초)는 그대로다.

## 6. 버스 번호만 다른 경로는 한 카드 (10-29)

사용자 요청(10-29): "같은 경론데 버스 번호만 다르면 그 안에 버스 번호를 여러 개 보여주는 식으로".
카카오는 한 구간을 지나는 대체 버스를 이미 `vehicles` 에 모아 주고, 서버는 그걸 `alt_vehicles` 로,
앱은 승차 행의 노선 칩으로 그린다. 그런데 카카오가 **버스만 다른 경로를 따로** 줄 때가 있어서
(신림역→서울대 5516 과 5528) 카드가 둘로 나뉘고 칸을 차지했다.

**같은 경로로 보는 기준**(`_same_shape`). 탑승 구간이 같은 수만큼 있고, 구간마다

- 수단이 같다. 지하철은 노선까지 같아야 한다(버스만 번호가 달라도 된다).
- 타는 정류장과 내리는 정류장 **이름이 완전히 같다**. 이름이 없으면 합치지 않는다.
- 탑승 시간 차이가 **5분 이하**다(`TRANSIT_MERGE_MAX_RIDE_DIFF_SECONDS`). 같은 곳 사이라도 돌아가는 버스는 따로 둔다.

좌표로 묶지 않는 이유(사용자 10-29 "이름으로 묶어. 완전히 동일할 때만"): 처음에는 300m 안이면 같은
정류장으로 봤다. 10-29 실측에서 5516 은 "신림사거리", 5528 은 "신림사거리.신림역"(200m)에서 탔는데,
이걸 한 카드에 넣으면 다른 정류장 버스를 같은 곳에서 기다리게 된다. 그래서 이 둘은 따로다. 같은 실측
두 구간(신림역→서울대·강남역)에는 이름까지 같은데 버스만 다른 경로가 없었다. 카카오가 그런 버스는
이미 한 구간의 `vehicles` 로 모아 주기 때문이다. 이 규칙은 그 밖의 경우를 위한 것이다.

**합친 카드**

- 대표는 가장 빠른 경로다. `key`·`minutes`·`segments` 는 대표의 것이다.
- 다른 경로의 버스는 그 구간의 `alt_vehicles` 에 붙는다(같은 정류장이다).
- `member_keys`: 합친 경로의 key 전부(대표가 처음). `minutes_max`: 합친 경로 중 가장 느린 분.
  합친 게 없으면 `member_keys` 는 key 하나, `minutes_max` 는 `minutes` 와 같다.
- `detail` 의 "(대체 N개)" 는 합친 버스까지 센다.
- 같은 노선 조합이 다른 정류장에서 또 오면 전처럼 빠른 것만 남긴다. 같은 정류장이면 그쪽에만 있던
  대체 버스를 더한다.

**저장된 경로 찾기.** 대표 버스는 날마다 바뀔 수 있다. `resolve_route` 는 일정의 `route_key` 를
`member_keys` 에서 찾고, **고른 key 를 그대로** 돌려준다(`route_choice_honored` 가 참으로 남는다).
계산은 합친 카드(대표) 기준이다. 경로 선택 화면의 기본 선택(`preferred_key`)도 `member_keys` 로 찾는다.

**실시간.** 버스 정류장 조회(`getStationByUid`)는 그 정류장의 모든 노선을 한 번에 준다. 그래서
대체 버스의 다음·그다음 도착(`alt_vehicles[].arrivals`, 대표 구간의 `arrivals` 와 같은 모양)을
**호출을 늘리지 않고** 붙인다.

**구버전 앱.** 새 필드는 무시되고, 합친 버스는 지금 있는 대체 노선 칩으로 보인다.

**남은 것(백엔드).** 이동 보정 학습은 `route_key` 로 묶어서, 같은 경로를 버스만 다르게 고른 일정끼리는
표본이 갈린다(P2 "이동 시간 학습 정교화"에서 다룬다). 심야·새벽 버스(N15, N75, 새벽A504)가 낮 일정에도
대체 노선이나 경로로 나온다(10-29 실측). 출발 시각으로 거르는 건 따로 한다.

# 대중교통 후보 고르기 (0.14.0)

경로 선택 화면(`GET /api/routes/candidates`)의 대중교통 후보를 3개에서 5개로 늘리고, 고르는 기준을
늘렸다. 3개일 때는 시간·환승·요금 기준만 들어가서 같은 노선을 조금씩 바꾼 비슷한 경로만 나왔다
(사용자 요청 10-29 "최대한 다양한 옵션이 나오게"). 카카오 호출 수는 그대로다. 한 번 받은 응답
안에서 고른다.

구현: `backend/apps/routing/clients.py` `_transit_pool`·`_transit_candidates`·`resolve_route` ·
테스트: `backend/apps/routing/tests/test_transit_variety.py`

## 1. 고르는 순서

카카오 응답을 노선 조합(구간마다 첫 노선을 이은 것, 예: `2호선>5513`)으로 묶고, 조합이 같으면 가장
빠른 것 하나만 남긴다. 그다음 아래 순서로 하나씩 담는다. 이미 담긴 경로면 건너뛴다. 동률이면 빠른 쪽이다.

| 순서 | 기준 |
| --- | --- |
| 1 | 가장 빠른 것 |
| 2 | 환승이 가장 적은 것 |
| 3 | 걷는 시간이 가장 짧은 것(집→정류장, 환승, 정류장→목적지 도보의 합) |
| 4 | 지하철만 타는 것 중 가장 빠른 것 |
| 5 | 버스만 타는 것 중 가장 빠른 것 |
| 6 | 지하철과 버스를 섞는 것 중 가장 빠른 것 |
| 7 | 요금이 가장 싼 것(요금을 모르는 경로는 뺀다) |
| 남는 칸 | 이미 담긴 경로에 없는 노선이 많은 것부터 |

- 5개가 차면 멈춘다. 그래서 1~6이 모두 다르면 요금 기준은 들어가지 못한다.
- 남는 칸에는 **너무 느린 경로를 넣지 않는다.** 가장 빠른 것의 1.5배 이상이거나 20분 이상 더
  걸리면 뺀다(`TRANSIT_FILL_MAX_RATIO`, `TRANSIT_FILL_MAX_EXTRA_SECONDS`). 1~7 기준 대표에는 이
  조건을 걸지 않는다. 30분 걸려도 환승 없는 버스를 고르는 사람이 있다.
- 남는 칸을 빠른 순으로 채우면 가장 빠른 경로의 뒤 버스만 바꾼 것들이 칸을 다 차지한다. 그래서 새
  노선 수를 먼저 본다.
- 응답의 대중교통 후보 순서는 전과 같이 전체 목록과 함께 빠른 순이다.

## 2. 배지

`badges` 에 `"최소 도보"` 가 새로 생겼다. 기준은 대중교통 후보 전체(추리기 전)에서 걷는 시간이 가장
짧은 것이고, 동률이면 모두 받는다. **배지는 최대 3개다**(순서: 최단 시간, 최소 비용, 최소 환승, 최소
도보). 경로 카드 한 줄에 들어가야 한다. `reason` 은 전처럼 첫 배지다.

## 3. 고른 경로로 알람 계산하기

`resolve_route` 는 이제 **추린 5개가 아니라 카카오 응답 전부에서** 고른 노선 조합을 찾는다. 그날
순위가 밀려 화면 목록에서 빠져도 카카오가 그 조합을 아직 주면 그 경로로 계산한다. 전에는 3개 안에
없으면 대중교통 최단으로 바꿨는데, 일부러 고른 느린 직행 버스 대신 빠른 경로로 계산하면 알람이 늦게
울린다. 카카오가 그 조합을 아예 주지 않을 때만 최단으로 바꾼다(`route_choice_honored: false`).

경로를 고르지 않은 일정(`best_route`)은 전과 같다. 도보와 대중교통 최단 중 빠른 쪽이다.

## 4. 앱

- `RouteMode.TRANSIT` 상한 3 → 5(`domain/model/RouteOption.kt`). **이 앱이 아니면 5개 중 빠른 3개만
  보인다.** 빠른 순으로 자르므로 환승 최소·도보 최소 경로가 빠질 수 있다. 서버와 앱을 같이 올린다.
- 대중교통 탭에 카드가 최대 5개다. 목록은 이미 세로 스크롤이다.
- 배지 문구 `"최소 도보"` 는 서버 문구 그대로 그린다(앱 변경 없음).

## 5. 늘어나는 것

- 응답 크기: 후보마다 미리보기 경로 좌표가 붙어서 대중교통 2개분이 늘어난다.
- 실시간 도착 정보(버스·지하철 API)는 최종 후보에만 붙이므로 조회가 최대 3개분 → 5개분으로 는다.
  캐시(버스 15초, 지하철 20초)는 그대로다.

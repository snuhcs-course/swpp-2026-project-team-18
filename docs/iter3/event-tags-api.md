# 일정 종류 직접 추가 API (BE-21)

화면 12-a 종류 드롭다운의 "+ 추가" 를 서버가 받는다(task.md B-8 · BE-21, 사용자 요청 11-04). 지금 앱은 누르면 "종류 직접 추가는 준비 중" 만 띄운다. 아래 5절대로 바꾸면 된다.
구현: `backend/apps/events/tags.py`, 모델 `EventTag.user`(마이그레이션 `events 0013`) · 테스트: `backend/apps/events/tests/test_event_tags.py` · 서버 0.19.0

## 1. 규칙

- 전역 종류 6개(수업, 시험, 발표, 기차·비행, 알바, 약속)는 그대로다. 사용자가 만든 종류는 **그 사용자에게만** 보인다.
- 이름은 앞뒤 공백을 지우고 가운데 공백을 하나로 줄인다. 1~20자.
- **같은 이름이면 새로 만들지 않고 있는 것을 200 으로 돌려준다**(대소문자 무시). 전역 "시험" 이 있는데 "시험" 을 만들면 전역 `exam` 이 온다. 앱은 201·200 구분 없이 돌려받은 종류를 고르면 된다.
- 사용자당 20개(409 `tag_limit`). 한도에 차도 이미 있는 이름은 200 으로 돌려준다.
- `default_tau` 는 0.5~0.999 또는 null. **null(생략)이면 프로필 기본 τ 를 따른다.** "+ 추가" 에서 τ 를 묻지 않아도 된다.
- `penalty_shape` 는 사용자 종류면 늘 `"linear"` 다.
- 키(`key`)는 서버가 만든다. `u` + 16진수 10자리(예 `u3f9a0c12be`). 일정 생성·수정의 `tag_key` 에 그대로 쓴다.
- 남이 만든 종류의 키를 `tag_key` 로 보내면 없는 종류와 같다(400 `invalid`, `details.tag_key`). 캘린더 가져오기도 같다.
- 모두 로그인 필요. 만들기·고치기·지우기는 사용자당 60회/시간(`event_tag`). 목록 조회는 세지 않는다.

## 2. 응답 모양

목록과 일정 응답의 `tag` 가 같은 모양이다. `custom` 이 새로 생겼다.

```json
{"id": 12, "key": "u3f9a0c12be", "label": "동아리", "default_tau": null, "penalty_shape": "linear", "custom": true}
```

- `custom`: 사용자가 만든 종류면 true. 전역 종류는 false.
- `default_tau`: 사용자 종류는 null 일 수 있다. 앱은 τ 칸에 "프로필 기본" 을 쓰면 된다(지금 `tagOptionsOf` 는 null 이면 빈칸).

## 3. 엔드포인트

| 요청 | 성공 | 오류 |
| --- | --- | --- |
| `GET /api/events/tags` | 200 배열. 전역 종류(정해진 순서) 다음에 내 종류(만든 순서) | |
| `POST /api/events/tags` `{label, default_tau?}` | 201 새 종류. 같은 이름이 이미 보이면 그 종류 **200** | 400 `invalid`(이름 비었음·20자 초과·τ 범위 밖), 409 `tag_limit` |
| `PATCH /api/events/tags/{key}` `{label?, default_tau?}` | 200 종류 | 404(전역·남의 종류·없는 키), 409 `tag_duplicate`(보이는 다른 종류와 이름이 같다), 400 `invalid` |
| `DELETE /api/events/tags/{key}` | 204 | 404 |

오류 본문은 공통 형식 `{"error": {"code", "message", "details"}}` 이다.

## 4. 고치거나 지우면

- **τ 를 바꾸면** 그 종류를 단 앞으로의 일정 알람을 경로 조회 없이 다시 섞는다(`planning.refresh.refresh_upcoming`, 카카오 0회). 이미 울렸거나 출발한 일정은 그대로 둔다. 이름만 바꾸면 알람은 그대로다.
- **지우면** 그 종류를 단 일정·반복 규칙은 종류 없음이 되고(`tag` null) 프로필 기본 τ 를 쓴다. 알람도 같은 방법으로 다시 섞는다. 지난 일정도 종류 없음이 된다.
- 새 알람은 앱의 정기 동기화가 기기에 다시 건다. 바로 반영하려면 응답을 받은 뒤 일정 목록을 다시 불러온다.
- 리스크 선택 화면의 "자동 조정" 문구(`risk-options` 의 `auto_adjusted`)는 τ 가 null 인 사용자 종류에 뜨지 않는다. 프로필 기본값을 그대로 쓰기 때문이다.

## 5. 앱 할 일 (프론트)

1. `AddEventScreen.TagDropdown` 의 "+ 추가": "준비 중" 안내 대신 이름 입력 창을 띄운다. 확인을 누르면 `POST /api/events/tags {label}`.
2. 201·200 이면 돌려받은 종류를 목록에 넣고(같은 `key` 가 이미 있으면 넣지 않는다) 그것을 고른다. 409 `tag_limit` 이면 메시지를 보여준다.
3. 목록(`GET /api/events/tags`)은 화면을 열 때 다시 받는다. 내 종류가 전역 종류 뒤에 붙어 온다.
4. `default_tau` 가 null 인 종류는 τ 칸에 "프로필 기본" 을 쓴다.
5. 내 종류 이름 바꾸기·지우기. 앱은 종류 드롭다운의 내 종류 줄 [편집] 으로 연다(11-10, task.md B). 관리 화면은 Figma 가 생기면 옮긴다.

**구버전 앱**은 `custom` 을 모르고 무시한다. 다른 기기에서 만든 종류도 목록 끝에 보이고 고를 수 있다.

## 6. 배포

`events 0013` 마이그레이션이 필요하다(배포 컨테이너가 시작할 때 `migrate` 가 돈다). 새 컬럼 `events_tag.user_id` 는 null 허용이라 구버전 코드가 같은 DB 에서 돌아도 쓰기가 깨지지 않는다. 기존 6개 행은 그대로 전역 종류다.

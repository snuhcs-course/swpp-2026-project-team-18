# 발표용 MVP 체크리스트

기준: **2026-10-05 / 앱·서버 0.9.0**.
목표는 로그인부터 알람 발화·준비 기록·이동·도착·리포트까지 같은 계정·기기로 완주하는 것이다.
강의 원본 시나리오는 Wiki의 `front-spec.md` 14절을 참고한다.

## 현재 검증 상태

| 대상 | 확인 결과 |
| --- | --- |
| 백엔드 | pytest 717건 통과; 임시 DB HTTP 스위트 8개·실패 0개, 외부 API 항목 일부 건너뜀 |
| Android | 단위 테스트 490건 통과, lint 오류 0건, 디버그 빌드 성공 |
| 공용 API | health 0.9.0; 데모 계정 인증·프로필·일정·루틴·리포트 조회, 장소 검색·경로 후보 정상 |
| 에뮬레이터 | `JIT_API_34` 실행; 정확한 목적지 좌표에서 120초 체류 후 도착 판정·관측 업로드 확인 |
| 로컬 E2E | 핵심 10단계 전체 실행 2회 통과(최종 275초): 실제 알람, 루틴 기록, GPS 출발·도착, 화면 유지, 리포트 |
| 발표 환경 | 공용 서버·실기기의 전체 완주는 추가 확인 필요 |

위 결과는 2026-10-05 확인 기록이다. 공용 API 행은 읽기 전용 검증이다.

## 자동 E2E

[데모 QA 실행 안내](../qa/demo/README.md)에 따라 에뮬레이터를 켜고 루트에서
`backend/.venv/bin/python qa/demo/run.py`를 실행한다. 알람 대기는 약 30초,
GPS 도착의 120초 체류는 유지한다. 영상·스크린샷·검증 결과는 Git에서 제외한다.

## 준비

- [ ] [앱 안내](../APP/README.md)에 따라 발표용 APK를 설치하고 공용 서버 주소를 확인한다.
- [ ] [기기 안내](device-setup.md)에 따라 한국 시간대·알림·정확한 위치·전체 화면 알림을 설정한다.
- [ ] 전용 시연 계정에 집, 준비 블록 2개, 가까운 목적지와 도보 경로를 준비한다.
  공용 `demo@demo.com`은 조회용으로 사용한다. 신림역 집 예시: 위도 37.484267, 경도 126.929745.
- [ ] 가상 GPS에 집·목적지·경로를 저장하고, 서버를 미리 깨워 로그인·목록 조회를 확인한다.

알람을 3~5분 뒤로 잡으려면 일정 시작을 대략 **현재 + 준비 + 이동 + 버퍼 10분 + 3~5분**으로 정한다.
최종 기준은 생성 후 서버가 계산한 알람 시각이다. 이미 과거면 더 늦은 일정으로 다시 만든다.
현재 앱에는 일정 수정 화면이 없으며, 시계를 바꾸지 않고 실제 시간으로 테스트한다.

## 기본 시나리오

로컬 QA에서 D08~D12의 핵심 흐름을 자동 확인했다. 아래 표는 발표 환경에서도 확인한다.
실행 후 단계별 결과·증거를 기록한다.

| ID | 조작 | 통과 기준 |
| --- | --- | --- |
| D01 | API 34 이상 기기에 설치·실행 | 로그인 화면 표시, 크래시 없음 |
| D02 | 전용 계정 가입·로그인·재실행 | 홈 진입, 로그인 유지 |
| D03 | 집·준비 시간 설정 | 저장·재진입 후 값 유지 |
| D04 | 준비 블록 생성·일정별 선택 | 저장 및 해당 일정 계산에 반영 |
| D05 | 장소·경로 선택 | 선택한 도착지·수단·경로 반영 |
| D06 | 미래 일정 생성·알람 확인 | 미래 알람과 준비·이동·버퍼 근거 표시; 확률 부족은 “학습 중” |
| D07 | 홈 메뉴·기기 예약 확인 | 등록 수·다음 알람이 해당 일정과 일치 |
| D08 | 앱을 배경으로 보내고 화면 잠금 | 예정 시각에 소리·알림·전체 화면 발화; 실제 시각·오차 기록 |
| D09 | 알람 해제·준비 블록 완료 | 알람 정지, 추적 시작, 준비 소요 기록 저장·업로드 |
| D10 | 가상 GPS로 출발·이동 | 출발 관측, 이동 상태·진행률·ETA 표시 |
| D11 | 목적지에서 2분 이상 체류 | 도착 관측 업로드, 도착 결과 화면 유지 |
| D12 | 관측·주간 리포트 확인 | 해당 계정 기록 반영, 표본 부족 시 이유 표시 |

GPS 판정 시간과 로그 확인은 [기기 안내](device-setup.md)를 따른다.
업로드는 홈 메뉴의 미전송 기록·로그 또는 자기 계정의 `GET /api/observations`로 확인한다.
**관측 업로드와 도착 화면 유지 모두** 통과해야 D11을 완료한다.

## 알려진 문제·제한

| 항목 | 현재 상태 |
| --- | --- |
| 도착 화면 | 서비스 종료·화면 재진입 후 도착 상태·시각 유지 확인; 앱 프로세스 재시작 후 복원은 미구현 |
| 추적 재시작 | 이동 상태·ETA 기준 초기화 |
| 지도 조작 | 연속 드래그·작은 핀치에서 과하게 튐 |
| 알람 설정 | 설정 버튼은 뒤로 가기만 함; 켬/끔·하루 첫 알람 규칙은 B-3 연결 필요 |
| 리스크 선택 | 안내 화면만 구현; 옵션 선택은 B-5 연결 필요 |
| 확률·최단 경로 | 관측 부족은 “학습 중”; 최단 경로는 선택한 수단 안에서 비교 |

## 추가 검증과 발표 준비

- [ ] 5분 미루기 재발화, 재부팅 후 알람 복원, 오프라인 관측 보관·복구 업로드를 확인한다.
- [ ] 추적 프로세스 복구와 계정 변경을 확인한다. Force stop은 자동 복구와 따로 기록한다.
- [ ] 실기기에서 절전·잠금·실제 GPS·화면 꺼짐 조건을 확인한다.
- [ ] 개인화를 시연하면 관측 → 학습 → 재계산 전후 결과를 확인한다.
  이동 학습 `train_models`는 공용 DB에 보정을 저장하므로 [백엔드 안내](../backend/README.md)를 따른다.
- [ ] APK·서버 버전을 확정하고 백업 영상을 준비한다. 가상 이동 기록은 실제 성능 평가와 구분한다.
- [ ] 시연 후 본인이 만든 미래 일정을 정리한다.

결과 기록은 다음 양식을 사용한다. D01~D12 모두 통과한 뒤 전체 완료로 표시한다.

```text
일시·담당자 / 앱·서버 버전·소스 커밋 / 기기·권한 / 계정·일정 ID:
단계 ID / 통과·실패·차단 / 기대와 실제 / 증거·관련 이슈:
예정·실제 발화 시각·오차 / 남은 작업·담당자:
```

기록·영상에 비밀번호나 토큰을 넣지 않는다.

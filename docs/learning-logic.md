## 0. 전체 공식

```
알람 = 일정 시작 − 버퍼 − (준비 + 이동 합성 분포의 τ 분위수)
```

- 준비와 이동을 각각 **분포**(평균 ± 흩어짐)로 만든 뒤 합친다(convolution).
- 합친 분포에서 τ 분위수를 잡는다. τ = 0.9 면 "10번 중 9번은 이 안에 끝나는 시간"이다.
- **준비의 τ 분위수와 이동의 τ 분위수를 따로 구해 더하지 않는다.** 따로 더하면 둘 다
  최악인 날을 가정하게 되어 알람이 지나치게 일러진다(τ 0.9 두 개를 더하면 결합 확신도는
  0.99 에 가깝다).
- 버퍼는 분포 밖에서 그대로 더한다. 처음에는 10분이고, 밤 학습이 지각 이력으로 4~15분
  안에서 조정한다(§3).
- 정시 도착 확률은 `P(준비 + 이동 ≤ τ 분위수 + 버퍼)` 다. 분포에 흩어짐이 실제로 있을 때만
  낸다. 없으면 `null` 과 이유 코드(`confidence_basis`)를 준다.

### 공통 섞기 규칙 (shrinkage)

```
새 추정 = w × 내 실측 + (1 − w) × 기존 추정,   w = n / (n + k)
```

표본(n)이 적으면 기존 추정을 많이 믿고, 쌓일수록 실측을 믿는다. 평균뿐 아니라 분산도
같은 가중으로 섞는다(표준편차를 선형으로 섞으면 분산이 과소평가된다).

| 재료 | 기존 추정 | k | 1개일 때 | 3개 | 5개 | 12개 |
| --- | --- | --- | --- | --- | --- | --- |
| GPS 출발 기준 준비 시간 | 블록·온보딩 추정 | 3 | 25% | 50% | 63% | 80% |
| 블록 기록(아침에 누른 기록) | 블록 신고 범위 | 5 | 17% | 38% | 50% | 71% |
| 경로 전용 이동 보정 | 전역 보정 | 5 | — (최소 3개) | 38% | 50% | 71% |
| 시간대 계수 | 1.0 | 5 | 17% | 38% | 50% | 71% |
| 걷는 속도 | 1.0 | 5 | 17% | 38% | 50% | 71% |

시간대 계수와 걷는 속도는 평균만 옮긴다. 흩어짐은 경로 보정의 것을 그대로 쓴다.

## 1. 준비 시간

믿는 순서: **GPS 출발 실측 > 블록 기록 > 온보딩 값**

### ① 사전값 (`_estimate_prep_prior`)

- **루틴 블록이 없으면** 온보딩에서 답한 준비 시간 하나(없으면 30분, `FALLBACK_PREP_MINUTES`).
  값 하나라 흩어짐은 0 이다.
- **블록이 있으면** 블록마다 신고 범위를 정규분포로 본다.
  - 예: 샤워 10~20분 → 평균 15, 표준편차 (20 − 10) / 4 = 2.5 (범위를 95% 구간으로 본다)
  - 블록 기록이 있으면 k = 5 로 섞는다. 5번 기록하면 신고값 : 실측 = 50 : 50.
  - 직렬 블록은 합치고(convolution), 병렬 블록(예: 세탁기 돌리기)은 "더 늦게 끝나는 쪽"
    (max)으로 계산한다.

학습에서 빼는 블록 기록(`usable_block_observations`):

- 일정을 "안 감" 으로 표시했다
- 같은 일정의 GPS 출발보다 늦게 찍혔다(나간 뒤에 눌러 이동 시간이 섞였다)
- 블록 신고 최소의 0.5배 미만 · 최대의 1.5배 초과(누르는 걸 잊었다가 한참 뒤에 눌렀거나
  안 한 블록을 바로 눌렀다)
- 사용자가 그 아침을 준비 학습에서 뺐다(아래 ②)

### ② GPS 출발로 보정 (`_with_gps_samples`)

하루 표본 1개:

```
그 일정의 첫 GPS 출발 시각 − 그 직전 마지막 알람 끈 시각
```

미루기 뒤 다시 울려 끈 경우 마지막으로 끈 시각부터 준비를 시작한 것으로 본다.

버리는 것:

- 출발지를 따로 고른 일정(집에서 준비하고 나간 아침이 아니다)
- 준비 시간을 뺀 일정(`include_prep` false) · "안 감" 으로 표시한 일정
- 사용자가 준비 학습에서 뺀 아침(`Event.prep_learning_excluded_at`, `manage.py
  exclude_prep_mornings` 로 붙이고 뗀다. 사용자 10-30 "80분 넘어가는 거 수기로 제외")
- GPS 오차 반경 150m 초과
- 출발 전에 알람을 끈 기록이 없는 일정
- 1분 미만 · 6시간 초과(짝이 잘못된 것)
- **정한 준비 시간의 0.5~1.5배 밖**(사용자 10-29 "55분 세팅한 거에서 지나치게 벗어난 건
  학습에서 제외"). 55분이면 27.5~82.5분만 쓴다. 기준은 블록 기록을 섞기 전의 정한 값(블록
  신고 범위·온보딩)이다. 섞은 값을 기준으로 쓰면 걸러진 표본이 다시 기준을 움직인다. 예전
  0.25~4배는 다시 잠든 아침까지 들어가 준비 시간이 지나치게 늘었다. 대가: 정한 값이 실제와
  크게 다르면 학습으로 고쳐지지 않으니 설정을 고쳐야 한다.

남은 것 중 최근 30개만 쓴다. k = 3 으로 섞는다 — 블록(k = 5)보다 빨리 믿는다. 사람이 누른
기록보다 GPS 출발을 더 믿기 때문이다. 30개가 상한이라 정한 값은 늘 9% 이상 남는다
(30 / 33 = 91%).

- 예: 사전값 40분, GPS 실측 1개 28분 → 40 × 0.75 + 28 × 0.25 = **37분**
- 예: 사전값 40분, GPS 실측 3개 평균 30분 → w = 0.5 → **35분**
- 예: 정한 값 55분, 실측 평균 65분 → 1개 57.5분, 3개 60분, 10개 62.7분, 30개 64.1분

흩어짐:

- 표본 1개면 표준편차를 만들 수 없어 사전값의 폭을 그대로 쓴다("한 번 재봤으니 변동성이
  없다"고 하면 안 된다).
- 2개부터 실제 흩어짐을 쓴다. 그래서 온보딩 값만 있어 흩어짐이 0 이던 사용자도 표본 2개가
  쌓이면 τ 에 따라 준비 시간이 움직이고 정시 확률이 나오기 시작한다.

블록 내역(샤워 몇 분 등)은 총량 비율로 늘이거나 줄여 화면에 보여 준다. 블록 기록은
"어디에 시간을 썼나"의 비율로만 남고, 총량은 GPS 쪽을 따른다.

### ③ 적용 조건 (`Event.prep_applies`)

- 사용자가 일정마다 고른 값(`include_prep`)이 먼저다(친구 집에서 자고 출발하는 아침에 준비를
  넣는 등).
- 고르지 않았으면 집에서 출발할 때만 넣는다. 출발지를 따로 고른 일정(`origin_lat` 있음)은
  준비 시간이 빠진다(`prep_source = not_from_home`).
- 준비를 넣었더라도 출발지를 따로 고른 일정의 GPS 출발은 ②의 학습 표본이 되지 않는다.

### ④ "학습"이 따로 없다

준비 시간에는 밤에 학습해 저장해 두는 모델이 없다. 알람을 계산할 때마다 쌓인 기록을 그
자리에서 읽어 계산한다. 다만 **기록을 올리는 것만으로는 알람이 다시 계산되지 않는다.**
알람에 실제로 들어가는 시점은 §4 를 볼 것.

## 2. 이동 시간

### ① 기본값

카카오가 준 예상 시간(점추정). 학습이 한 번도 돌지 않아 보정이 하나도 없으면 원값 그대로이고
흩어짐이 0 이라 τ 를 바꿔도 이동 시간은 변하지 않는다 — 변동성을 모르는데 움직이면 거짓이다.

### ② 학습 재료 (`collect_travel_samples`)

한 일정의 **GPS 출발 → GPS 도착** 쌍.

```
실제 소요 = 도착 − 출발
비율     = 실제 소요 ÷ 그 결정 시점의 카카오 예상(PlanRevision.route_minutes_raw)
```

같은 종류가 여러 건이면 가장 이른 것을 쓴다(처음 집을 벗어난 시점, 처음 목적지에 든 시점).

버리는 것:

- "안 감" 으로 표시한 일정
- 직접 누른 판정(수동 도착). 누른 시각이 실제보다 늦기 쉬워 이동이 길게 학습된다.
  리포트 채점에만 보조로 쓴다.
- 이동 중에 경로를 바꾼 일정(`TripReroute`, 0.16.0). 결정 시점 원값이 원래 경로의 것이라
  실측과 맞지 않는다. 준비·버퍼·리포트에는 그대로 쓴다.
- GPS 오차 반경 150m 초과
- 출발·도착 한쪽만 있음
- 1분 미만 또는 역순
- 결정 시점 계획에 카카오 원값이 없음
- 비율 0.25~4배 밖

### ③ 밤 학습: 한 비율을 세 단계로 푼다 (`update_route_corrections`)

비율 하나에 걷는 속도, 시간대(아침 지연), 경로 자체의 성질이 섞여 있다. 앞 단계의 계수를
예측에 먼저 곱한 뒤 다음 단계를 배운다. 그래야 같은 지연이 두 번 들어가지 않는다.

1. **걷는 속도(사용자별, `UserTravelProfile`).** 경로 key 가 `walk` 인 일정만 쓴다. 대중교통
   기록은 대기·차내 시간이 섞여 걷는 속도를 가려낼 수 없다. 실제 ÷ 카카오 도보 예측의 평균을
   저장한다. 그다음 모든 표본의 예측을 "원값 + 걷는 분 × (걷는 속도 − 1)" 로 고친다.
   대중교통은 도보 구간(집→정류장, 환승, 정류장→목적지, `PlanRevision.walk_minutes_raw`)만
   고친다. 이 칸이 생기기 전 이력의 대중교통은 걷는 분을 몰라 고치지 않는다.
2. **시간대 계수(전역, 이동 종류별).** 종류(walk·transit·car·bicycle)는 경로 key 로 정한다
   (`travel_kind`, `travel_mode` 는 "버스+지하철" 같은 화면용 이름이다). 구간은 결정 시점
   계획의 출발 시각(`depart_by`)으로 고른다. 값은 **그 구간 평균 비율 ÷ 그 종류 전체 평균
   비율**이라 1.0 이면 "평소와 같다" 는 뜻이다.
3. **경로·전역 보정.** 1·2를 곱한 예측과 실제의 비율로 배운다.
   - `factor` = 비율의 평균
   - `sd_minutes` = 보정 **후에** 남는 오차(`실제 − 예상 × factor`)의 표준편차. 보정 전
     오차를 쓰면 체계적 편향과 변동성을 구분하지 못한다.

시간대 구간:

| 구간 | 시각 | `hour_bucket` |
| --- | --- | --- |
| 출근 | 06:00~08:59 | 6 |
| 낮 | 09:00~16:59 | 9 |
| 퇴근 | 17:00~19:59 | 17 |
| 밤 | 20:00~05:59 | 20 |

저장하는 행(`RouteCorrection`, 걷는 속도만 `UserTravelProfile`):

| 무엇 | 묶는 기준 | 만드는 조건 |
| --- | --- | --- |
| 경로 보정 | 경로 · 수단 · 주중/주말 | 표본 3개 이상 |
| 전역 보정 | 전체 경로 · 수단 | 항상 |
| 최후 전역 | 전체 | 항상(새 수단을 처음 쓸 때) |
| 시간대 계수 | 이동 종류 · 시간대 구간 · 주중/주말 | 항상 |
| 걷는 속도 | 사용자 | 도보 일정이 있을 때 |

경로 보정과 시간대 계수는 **사용자별이 아니라 공유**다. 2호선이 아침에 얼마나 지연되는지는
누가 타도 같다. 걷는 속도만 사람마다 다르다. 경로·전역 보정은 이제 시간대를 나누지 않는다
(`hour_bucket = -1`). 예전 시(時) 단위 행은 전체 재학습 때 지워진다.

### ④ 적용 (`estimate_travel`)

```
이동 = (원값 + 걷는 분 × (걷는 속도 − 1)) × 시간대 계수 × 경로 보정,   흩어짐 = sd_minutes
```

- **걷는 속도**: 1.0 + w × (기록 − 1) 을 0.7~1.5 로 자른다. 도보 경로는 원값 전체에,
  대중교통은 걷는 분에만 곱한다. 자동차·자전거는 곱하지 않는다.
- **시간대 계수**: 1.0 + w × (기록 − 1). 구간은 **계획한 출발 시각**(일정 시작 − 버퍼 −
  카카오 원값)으로 고른다. 실제 출발 시각은 이 계산의 결과라 아직 모르므로 근사한다. 구간이
  몇 시간 단위라 몇 분 차이는 거의 영향이 없다.
- **경로 보정**: 가장 구체적인 행부터 찾는다(수단·요일 일치 → 수단만 일치 → 아무거나).
  경로 전용과 전역을 k = 5 로 섞는다. 표본 3개짜리 경로 값을 그대로 믿으면 우연히 막혔던
  하루가 알람을 크게 당긴다.
- 시간대 계수 × 경로 보정은 0.25~4 로 자른다(학습 범위와 같다).
- 예: 카카오 30분(그중 도보 10분), 걷는 속도 기록 1.4·표본 5 → ×1.2, 출근 시간대 기록
  1.1·표본 5 → ×1.05, 이 경로 factor 1.2(표본 5)·전역 1.0 → ×1.1
  → (30 + 10 × 0.2) × 1.05 × 1.1 = 32 × 1.155 ≈ **37분**

이동 중 경로 바꾸기 판정(`planning/live_switch.py`, 0.16.0)도 같은 식으로 도착을 예상한다.
지금 시각의 시간대를 쓰고, τ 분위수가 아니라 평균을 쓴다.

## 3. 버퍼 (`buffers.py`, 밤 학습)

```
처음 10분 → 지각 이력으로 4~15분 안에서 조정
```

τ 가 이미 준비·이동의 흔들림을 다룬다. 모델이 약속한 정시 확률만큼은 늦을 수 있다. 그 지각까지
버퍼로 막으면 위험을 두 번 센다. 그래서 버퍼는 지각 횟수 자체가 아니라 **모델이 약속한 것과
실제의 차이**를 본다.

| 판단 | 조건 | 바꾸는 양 |
| --- | --- | --- |
| 늘림 | 지각이 2번 이상이고, 약속한 지각 수 Σ(1 − 정시 확률)보다 1번 이상 많다 | 지각 분 중앙값(1~5분) |
| 줄임 | 지각이 없고, 모든 아침이 계획한 도착(일정 시작 − 버퍼)보다 먼저 왔다 | 2분 |
| 그대로 | 그 밖 | |

- 직전 조정 **뒤에** 결정된 아침 중 최근 10번을 본다(90일 안). 3번 미만이면 그대로다. 한 번
  바꾸면 새 버퍼로 아침이 3번 쌓일 때까지 그대로다.
- 지각·여유는 주간 리포트와 같은 정의다(일정 시작 − 실제 도착, GPS 판정이 먼저).
- 버퍼·정시 확률은 결정 시점 계획에서 읽는다. 정시 확률이 없는 계획은 τ 를 약속으로 본다.
- 하한 4분: 도착 판정이 목적지 100m 안이라 자리에 앉기까지 몇 분이 더 든다(사용자 결정 10-28).
- 조정 기록은 `BufferAdjustment`(늘린 이유 "약속보다 잦은 지각", 줄인 이유 "쓰지 않은 버퍼")다.
  주간 리포트가 "버퍼 n분 → m분" 이유를 이 행으로 쓴다. 화면에는 `buffer_source` 가 `fixed`(조정 전) 또는 `learned` 로 나간다.

## 4. 언제 알람에 반영되나

### 밤 배치 (`train_models`)

`migrate --check` 가 먼저 돈다. 운영 DB에 main 의 마이그레이션이 없으면 여기서 멈춘다(학습·쓰기
전이라 데이터는 그대로다).

1. 이동 보정: 걷는 속도 → 시간대 계수 → 경로·전역 보정(§2 ③)
2. 전역 아티팩트, 3. 개인 아티팩트 — `prediction.ModelArtifact` 다. **알람 계산은 이것을
   읽지 않는다.**
4. 안전 버퍼 조정(§3)
5. 모든 사용자의 **앞으로 7일** 일정 알람을 **카카오 경로 조회 없이** 다시 계산한다
   (`refresh.refresh_after_learning`). 마지막 계산 때 받은 카카오 원값(과 걷는 분)은 그대로
   두고 분포만 다시 섞으므로 카카오 쿼터(일 1,000건)를 쓰지 않는다. 그날 올라온 GPS 출발·
   블록 기록도 이때 들어간다. 결과가 같으면 저장하지 않는다(화면의 "N분 전 계산"이 매일
   바뀌지 않는다).

다시 계산하지 않는 일정:

- 알람이 이미 울렸거나 이미 출발한 일정(그 아침의 결정은 끝났다)
- **3시간 안에** 알람이 울릴 일정 → 앱의 경로 갱신 워커가 실제 경로로 다시 계산하고 기기
  알람도 다시 건다
- 계산 불가 상태(집 없음 등)이거나 경로 원값이 지금 계획과 맞지 않는 일정 → 경로부터 다시
  구해야 한다
- 7일보다 먼 일정 → 7일 안에 들어오는 날 밤에 계산된다
- 사용자당 가까운 일정부터 최대 50개

### 그 밖에 다시 계산되는 때

| 언제 | 방식 |
| --- | --- |
| 일정을 만들 때, 출발지·목적지·고른 경로를 바꿀 때 | 카카오 경로 조회(`compute_and_store`) |
| 일정 시각·τ·준비 포함만 바꿀 때 | 지금 원값으로 다시 섞기(`refresh_edited`), 카카오 0회 |
| 루틴 블록을 만들거나 고치거나 지울 때 | 앞으로의 일정 다시 섞기(`refresh_upcoming`), 카카오 0회 |
| 준비 학습에서 아침을 빼거나 되돌릴 때(`exclude_prep_mornings`) | 그 사용자 다시 섞기 |
| 집 주소를 바꿀 때 | `recompute_for_user` |
| 알람 3시간 전부터 | 앱의 경로 갱신 워커 |
| 사용자가 "다시 계산" 을 누를 때 | `POST /api/events/{id}/recompute` |

### 예시

1. 화요일 7:40 알람을 끄고 8:08 에 집을 나감 → "준비 28분" 기록이 서버에 올라간다.
2. 이 순간 수요일 알람은 아직 옛 값이다(기록만 올라갔고 다시 계산하지 않았다).
3. 그날 밤 배치가 수요일 알람을 다시 계산하면서 28분을 읽어 반영한다.
4. 화요일 낮에 수요일 일정을 수정했다면 그때 바로 반영된다.

### ⚠️ 실제 실행 시각

`train-models.yml` 의 예약은 매일 23:17(KST)이지만 GitHub 예약 실행은 붐비면 늦게 시작한다.
최근 예약 실행(KST):

| --- | --- | --- |
| 10/24 | 03:23 | 성공 |
| 10/25 | 02:28 | 성공 |
| 10/26 | 02:39 | 성공 |

04:26 에 돌면 07:26 이전 알람은 "3시간 안" 이라 밤 배치가 건드리지 않고 앱의 경로 갱신

Render 예약 작업으로 옮기는 방법이 있다.

main 에 마이그레이션이 있는 커밋을 올리면 배포까지 마친 뒤에 밤 학습이 돌아야 한다. 배포가
늦으면 그날 밤 학습이 10/30 처럼 멈춘다.
